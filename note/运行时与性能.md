# JavaScript 运行时与性能 — 完整笔记

> 整理日期：2026-07-27  
> 分类：js-basics  
> 学习目标：理解性能成本如何产生，而不是背诵引擎名称和优化 API。

## 一句话总结

JavaScript 性能问题，本质上都是某种资源不够用了：CPU 时间不够，主线程没有空闲，内存无法及时回收，或者浏览器无法在一帧内完成布局与绘制。

分析性能时，不要先问“该用哪个优化 API”，而要先找出完整的因果链：

```text
代码做了什么工作
→ 这项工作由谁执行
→ 占用了 CPU、主线程还是内存
→ 为什么影响用户体验
→ 哪一段工作可以减少、推迟或转移
```

## 0. 先建立完整的运行模型

### 0.1 一段 JavaScript 是怎样变成页面的

假设页面中有这样一段代码：

```js
button.addEventListener('click', () => {
  const total = calculateTotal(products);
  result.textContent = total;
});
```

用户点击按钮以后，背后并不是只有“执行 JavaScript”这一件事，而是经历了以下过程：

```text
浏览器接收到点击
→ 事件回调进入任务队列
→ 主线程取出任务
→ V8 执行 calculateTotal
→ JavaScript 修改 DOM
→ 浏览器重新计算受影响的样式
→ 必要时重新布局
→ 绘制发生变化的内容
→ 合成最终画面
```

如果 `calculateTotal` 执行了 300ms，后面的 DOM 更新、布局和绘制就只能等待。用户会感觉按钮“点了没反应”。

因此，JavaScript 的性能不能只看函数执行是否正确，还要看它占用主线程多长时间，以及是否给浏览器留下了处理输入和渲染的机会。

### 0.2 V8 和浏览器不是一回事

V8 是 JavaScript 引擎，主要负责：1）把 JavaScript 源码解析成引擎能够执行的形式； 2）执行函数和表达式； 3）管理 JavaScript 对象使用的内存； 4）优化频繁执行的代码； 5）回收不再可达的对象。

浏览器还包含大量 V8 之外的能力：1）DOM 和 CSSOM； 2）网络请求； 3）定时器； 4）事件循环； 5）样式计算、布局、绘制和合成； 6）用户输入处理。

例如 `setTimeout` 不是 V8 自己计时：

```js
setTimeout(() => {
  console.log('done');
}, 1000);
```

浏览器负责计时。时间到达后，浏览器把回调对应的任务放进队列；主线程有空时，V8 才执行这个回调。

所以 `1000ms` 表示“至少等待这么久以后获得进入队列的资格”，不表示回调一定会在第 1000ms 精确运行。如果主线程仍被长任务占用，它只能继续等待。

### 0.3 主线程为什么是性能分析的中心

浏览器可以使用多个线程处理网络、图片解码等工作，但以下重要工作通常需要在主线程上协调或执行：1）JavaScript； 2）用户事件回调； 3）DOM 操作； 4）样式计算； 5）布局； 6）绘制准备。

这些工作不是同时发生，而是在同一条时间线上排队：

```text
| JS 任务 | 样式 | 布局 | 绘制 | 点击回调 | JS 任务 |
```

只要前面的工作没有结束，后面的工作就不能及时开始。这就是长 JavaScript 任务会同时造成输入延迟和动画掉帧的根本原因。

### 0.4 三类性能问题

#### CPU 问题

程序做了太多计算，例如：1）在每次输入时遍历十万条数据； 2）使用复杂度过高的算法； 3）重复计算本来可以复用的结果； 4）同一个回调被高频触发。

结果是 JavaScript 长时间占用 CPU 和主线程。

#### 内存问题

程序持续申请内存，或者无用对象仍然被引用：1）热点循环不断创建临时对象； 2）缓存没有容量上限； 3）监听器和定时器没有清理； 4）已删除的 DOM 仍被 JavaScript 引用。

结果可能是 GC 频繁、内存持续增长，甚至页面崩溃。

#### 渲染问题

程序让浏览器反复执行昂贵的页面更新：1）循环中交替读取和修改布局； 2）一次创建几万个 DOM 节点； 3）动画改变会触发布局的属性； 4）页面存在大面积重复绘制。

结果是一帧内无法完成工作，用户看到掉帧和卡顿。

这三类问题可能互相影响。例如一次创建大量 DOM，既消耗 CPU，也占用内存，还会增加布局和绘制成本。

## 1. JavaScript 代码是怎样执行的

### 1.1 为什么不能只说“JavaScript 是解释型语言”

如果引擎每次遇到同一段代码，都从头分析并用最通用的方式执行，频繁运行的程序会非常慢。反过来，如果页面刚打开就把所有代码做最高级别优化，启动时间又会很长，而且很多代码可能永远不会执行。

现代 JavaScript 引擎采用分层策略：

```text
源码
→ 解析为 AST
→ 生成字节码
→ 尽快开始执行
→ 收集真实运行信息
→ 找出热点代码
→ 将热点代码优化为机器码
```

它同时兼顾了两件事：1）冷代码快速启动，不花太多时间优化； 2）热代码充分优化，让长期运行更快。

### 1.2 解析：从字符串到 AST

引擎拿到的源码最初只是一串字符：

```js
const total = price * count;
```

解析器会识别出声明、标识符和运算关系，形成抽象语法树 AST。可以把它简化理解为：

```text
变量声明
├── 变量：total
└── 初始值：乘法表达式
    ├── price
    └── count
```

AST 不是为了展示给开发者，而是让引擎从“文本”过渡到“程序结构”。语法错误也会在这个阶段被发现：

```js
const = 1; // 无法形成合法语法结构
```

解析大型脚本同样需要 CPU 时间。即使代码最终没有执行，只要被下载并解析，也可能产生启动成本。这也是代码分割能够改善启动性能的原因之一：当前页面不需要的代码，可以暂时不下载、不解析、不编译。

### 1.3 字节码与快速启动

V8 中的 Ignition 会把 AST 转换成字节码。字节码比源码更接近执行指令，但仍然是与具体 CPU 相对独立的中间形式。

为什么不直接把所有代码编译成高度优化的机器码？因为优化需要分析和时间，而且缺少真实类型信息。

例如：

```js
function add(a, b) {
  return a + b;
}
```

`+` 可能表示数字相加，也可能表示字符串拼接：

```js
add(1, 2);       // 3
add('1', '2');   // "12"
```

函数还没运行时，引擎无法确定它最常接收哪种数据。先执行字节码，可以快速启动，同时观察真实使用情况。

### 1.4 JIT 与热点代码

JIT 是 Just-In-Time Compilation，即即时编译。

假设一个函数被重复调用十万次，而且参数始终是数字：

```js
function add(a, b) {
  return a + b;
}

for (let i = 0; i < 100_000; i += 1) {
  add(i, i + 1);
}
```

引擎会收集类型反馈：`a` 和 `b` 长期都是数字。函数成为热点以后，TurboFan 可以基于这个事实生成更专门的机器码，减少每次都进行通用类型判断的成本。

这里的核心不是记住组件名称，而是理解优化成立的条件：

```text
同一段代码频繁执行
→ 运行数据表现稳定
→ 引擎形成类型和结构假设
→ 生成针对这些假设的高效代码
```

### 1.5 反优化为什么发生

优化代码依赖假设。如果运行情况发生变化，假设就可能失效：

```js
function add(a, b) {
  return a + b;
}

// 长期传数字
for (let i = 0; i < 100_000; i += 1) {
  add(i, i + 1);
}

// 突然传字符串
add('hello', 'world');
```

之前针对数字加法生成的代码不能直接处理字符串拼接。引擎需要退回能够处理更多情况的代码，这就是反优化 Deoptimization。

反优化不是错误，也不代表传不同类型一定会造成严重性能问题。它是动态语言保证正确性的正常机制。只有当它发生在真正的热点路径，并且工具证明它带来显著成本时，才值得针对性处理。

### 1.6 启动性能与运行性能的取舍

引擎必须在两种成本之间平衡：1）编译得越充分，单次运行可能越快，但启动前等待越久； 2）编译得越简单，启动越快，但热点代码长期执行可能较慢。

分层编译正是这个取舍的结果。

对于业务开发，更直接的启示是：1）减少首屏不需要的 JavaScript，比研究微小语法差异更有价值； 2）保持热点代码输入和对象结构相对稳定，有利于引擎优化； 3）不要为了猜测引擎行为牺牲代码正确性和可读性； 4）是否存在问题，应通过 Performance 和性能分析器验证。

## 2. 对象为什么有快慢之分

### 2.1 JavaScript 对象给引擎带来的难题

静态语言中的对象结构通常在编译时就比较明确。JavaScript 对象却可以随时改变：

```js
const user = {};
user.name = 'Alice';
user.age = 18;
delete user.name;
user.role = 'admin';
```

如果每次执行 `user.age`，引擎都必须在动态结构中从头查找属性，访问成本会很高。

V8 会尝试为结构相同的对象建立可复用的内部描述，通常称为 Hidden Class，也常叫 Shape 或 Map。它不是 JavaScript 能直接访问的 `class`，而是引擎内部用来描述对象布局的数据结构。

### 2.2 Hidden Class 是怎样形成的

观察下面的对象创建过程：

```js
const user = {};
user.name = 'Alice';
user.age = 18;
```

可以把内部结构变化简化成：

```text
空对象结构 C0
  └── 添加 name → 结构 C1
        └── 添加 age → 结构 C2
```

另一个对象按照相同顺序添加相同属性时，可以沿用同一条结构转换路径：

```js
const anotherUser = {};
anotherUser.name = 'Bob';
anotherUser.age = 20;
```

两个对象的属性值不同，但布局相似，引擎更容易复用属性位置等信息。

### 2.3 为什么属性顺序可能产生不同结构

下面两个对象最后都有 `name` 和 `age`：

```js
const a = {};
a.name = 'Alice';
a.age = 18;

const b = {};
b.age = 20;
b.name = 'Bob';
```

但它们经历的结构转换不同：

```text
a：空 → name → name + age
b：空 → age  → age + name
```

因此它们可能拥有不同 Hidden Class。更稳定的创建方式是让同类对象从一开始就以相同顺序初始化：

```js
function createUser(name, age) {
  return { name, age };
}
```

这不是要求业务代码为了性能把每个对象都写成完全一致，而是解释为什么大量同类对象结构稳定时，引擎更容易优化。

### 2.4 Inline Cache 如何加速属性访问

假设有函数：

```js
function getName(user) {
  return user.name;
}
```

第一次执行时，引擎需要确认 `user` 的结构，并找到 `name` 的位置。随后可以在这个访问位置记录类似信息：

```text
如果传入对象的 Hidden Class 是 C2
那么 name 在已知位置
```

下一次传入相同结构的对象时，就不必走完整的通用查找流程。这种在代码访问位置缓存查找结果的机制叫 Inline Cache，简称 IC。

### 2.5 单态、多态和超多态

如果 `getName` 总是接收同一种结构：

```js
getName({ name: 'A', age: 18 });
getName({ name: 'B', age: 20 });
```

这个访问位置是单态的，缓存逻辑最简单。

如果它接收少量不同结构：

```js
getName({ name: 'A' });
getName({ id: 1, name: 'B' });
```

缓存可以记录多种结构，称为多态。

如果同一位置接收大量完全不同的结构，引擎可能无法继续为每一种情况生成高效的专门路径，进入超多态状态，转而使用更通用的属性查找。

完整因果链是：

```text
对象结构稳定
→ Hidden Class 可复用
→ Inline Cache 容易命中
→ 属性访问更容易被优化
```

### 2.6 删除属性为什么可能影响优化

频繁 `delete` 会改变对象结构：

```js
delete user.age;
```

在某些情况下，对象可能进入更通用的字典式属性存储，使动态修改更容易，但访问不再享受相同的结构优化。

如果业务上只是表示“当前没有值”，并且对象处于性能热点，可以考虑保持结构：

```js
user.age = undefined;
```

但二者语义并不完全相同：

```js
'age' in user; // 赋值 undefined 后是 true，delete 后是 false
```

因此不能为了性能盲目替换，必须先保证业务语义正确。

### 2.7 实际开发应该怎么做

合理原则只有三条：1）同一类高频对象尽量用一致方式初始化； 2）热点调用位置尽量避免毫无规律地混入大量完全不同的数据结构； 3）只有性能分析证明对象访问是瓶颈时，才针对 Hidden Class 和 IC 调整代码。

对于绝大多数业务，减少一次不必要的网络请求、避免一次十万条数据遍历，收益都远大于微调某个普通对象的属性顺序。

## 3. JavaScript 的内存模型

### 3.1 内存管理到底在管理什么

程序运行时需要保存很多数据：1）当前执行到哪个函数、哪一行代码； 2）函数的参数和局部变量； 3）对象、数组、字符串等动态数据； 4）对象之间的引用关系； 5）编译后的字节码和机器码。

这些数据的生命周期不同。有些只在一次函数调用期间存在，有些会被整个应用长期使用。引擎需要不断申请、使用和回收内存：

```text
分配内存
→ 写入和读取数据
→ 数据失去用途
→ 判断数据是否仍可访问
→ 回收并复用空间
```

JavaScript 提供自动垃圾回收，但“自动”只代表回收动作由引擎完成。对象之间建立什么引用、引用何时断开，仍然由程序结构决定。

### 3.2 调用栈保存函数执行状态

每调用一个函数，引擎都要记住这次调用的执行状态。可以把它理解成一个栈帧：

```js
function multiply(a, b) {
  return a * b;
}

function calculate(price, count) {
  const total = multiply(price, count);
  return total;
}

calculate(10, 3);
```

执行过程可以简化为：

```text
调用 calculate
调用栈：[calculate]

calculate 调用 multiply
调用栈：[calculate, multiply]

multiply 返回
调用栈：[calculate]

calculate 返回
调用栈：[]
```

栈帧中会保存返回位置、参数、局部状态等信息。函数返回以后，对应栈帧退出。

递归调用如果没有及时结束，会持续增加栈帧：

```js
function recurse() {
  recurse();
}

recurse(); // 最终 RangeError: Maximum call stack size exceeded
```

这叫栈溢出。它和堆内存泄漏不是一回事：前者是调用层级过深，后者是对象长期无法回收。

### 3.3 堆保存动态对象

对象的大小和生命周期通常无法只根据函数调用顺序决定：

```js
function createUser(name) {
  return {
    name,
    preferences: {
      theme: 'dark'
    }
  };
}

const user = createUser('Alice');
```

`createUser` 已经返回，但返回的对象仍被外部变量 `user` 引用，所以对象必须继续存在。这样的动态数据通常存放在堆中，由垃圾回收器管理。

常见教学会说“基本类型在栈，对象在堆”。这句话可以帮助入门，但不能当作完整规范：1）ECMAScript 规定的是语言行为，不强制引擎使用某种物理存储方式； 2）引擎可能进行寄存器分配、逃逸分析和其他优化； 3）字符串等值的内部实现也可能比“直接放栈上”复杂。

面试中真正重要的是值语义和引用关系，而不是猜测某个变量的物理地址。

### 3.4 值与引用关系

基本类型赋值后，两个变量的值彼此独立：

```js
let a = 1;
let b = a;
b = 2;

console.log(a); // 1
```

对象赋值会让两个变量指向同一个对象：

```js
const a = { count: 1 };
const b = a;

b.count = 2;
console.log(a.count); // 2
```

可以把它画成：

```text
a ─┐
   ├──→ { count: 2 }
b ─┘
```

执行 `b = null` 只会断开 `b` 这条引用：

```text
a ───→ { count: 2 }
b ───→ null
```

对象仍被 `a` 引用，所以不能回收。只有所有从活动程序出发的引用路径都消失，对象才可能成为垃圾。

### 3.5 可达性是 GC 的判断依据

垃圾回收器无法理解“这个对象业务上已经没用了”。它只能判断：对象能否从一组根引用出发被找到。

这些起点称为 GC Root，常见来源包括：1）全局对象及全局变量； 2）当前调用栈中的局部变量和参数； 3）活跃闭包捕获的变量； 4）宿主环境仍在使用的回调和对象。

例如：

```js
const app = {
  currentPage: {
    panel: {
      data: new Array(100_000).fill('x')
    }
  }
};
```

引用链是：

```text
全局作用域
→ app
→ currentPage
→ panel
→ data
```

只要 `app.currentPage` 仍指向页面对象，后面的整条对象图都是可达的。

执行：

```js
app.currentPage = null;
```

如果没有其他引用指向原页面对象，这条对象图就不再能从根到达，可以在未来某次 GC 中被回收。

### 3.6 闭包为什么会延长变量生命周期

```js
function createCounter() {
  let count = 0;

  return function increment() {
    count += 1;
    return count;
  };
}

const counter = createCounter();
```

`createCounter` 已经执行结束，但返回的 `increment` 仍然需要访问 `count`。引擎不能销毁这部分词法环境，否则下次调用 `counter()` 就无法得到正确结果。

引用关系可以理解为：

```text
全局变量 counter
→ increment 函数
→ 闭包环境
→ count
```

这不是泄漏，而是闭包应有的语义。如果 `counter` 以后不再被引用，函数和它捕获的环境也可以一起回收。

### 3.7 排查内存问题为什么要看保留链

假设快照中发现一个占用很大的数组。仅知道数组很大并不能解释为什么它没有回收，真正的问题是：

```text
谁仍然引用它？
这个引用为什么没有在生命周期结束时断开？
```

开发者工具中的 Retainer Chain 就是从对象反向追踪到 GC Root 的引用路径：

```text
Window
→ 全局 store
→ 页面缓存 Map
→ 已关闭页面实例
→ largeData
```

修复对象通常不是最末端的 `largeData`，而是删除 Map 中已经失效的页面实例，让整条引用链断开。

## 4. 垃圾回收机制

### 4.1 为什么不能在对象“不用了”时立刻回收

从开发者视角看，可能已经不会再读取某个对象；但引擎不能预测未来代码，也不理解业务含义：

```js
const cache = { result: createLargeResult() };

// 目前没有读取 cache.result，未来是否还会读取？
```

只要对象仍然可达，引擎就必须假设程序将来可能使用它。垃圾回收只能安全地回收“从根已经无法到达”的对象。

### 4.2 引用计数为什么不够

引用计数为每个对象记录被引用次数，次数归零时回收。它直观，但难以处理循环：

```js
let a = {};
let b = {};

a.other = b;
b.other = a;

a = null;
b = null;
```

两个对象彼此引用，但外部已经无法访问它们：

```text
GC Root    { A ↔ B }
   ╳         内部互相引用
没有路径连接到这个环
```

从可达性角度看，它们都是垃圾；只看引用次数，它们的计数却不为零。

现代 JavaScript 引擎的核心判断建立在从根进行图遍历，而不是简单引用计数上。

### 4.3 标记清除如何工作

标记清除 Mark-Sweep 可以简化为两步：1）从所有 GC Root 出发，遍历并标记能够到达的对象； 2）扫描堆，回收没有被标记的对象。

假设对象关系是：

```text
Root → A → B

C ↔ D
```

从 Root 能走到 `A` 和 `B`，它们被标记为存活。`C` 和 `D` 虽然互相引用，但从根不可达，因此都可以回收。

这也解释了一个常见误区：

> 循环引用本身不等于内存泄漏。只有循环中的对象仍能从某个根到达时，它们才会继续存活。

### 4.4 为什么要分代

实际程序中的对象寿命分布并不均匀：1）函数内部的临时数组、参数包装和中间结果，通常很快死亡； 2）全局状态、应用配置、长期缓存，可能存活很久。

如果每次回收都扫描整个堆，会在大量短命对象上反复做昂贵的全堆检查。

分代垃圾回收利用“多数对象朝生夕死，少数对象长期存活”的经验规律，把堆划分成不同区域：1）**新生代**：新创建、预期寿命短的对象； 2）**老生代**：经过多轮回收仍然存活的对象。

不同区域使用适合其对象特点的回收策略。

### 4.5 新生代与 Minor GC

新生代中死亡对象通常很多。V8 可以把新生代的一部分看成当前分配区，另一部分看成复制目标区。

回收时：1）从根和老生代指向新生代的引用出发，找到仍存活的新对象； 2）把少量存活对象复制到目标空间； 3）原空间整体清空； 4）两块空间交换角色。

示意：

```text
回收前：
From [A 活][B 死][C 死][D 活]
To   [                         ]

复制存活对象：
From [A 活][B 死][C 死][D 活]
To   [A 活][D 活               ]

交换后：
新的 From [A 活][D 活          ]
新的 To   [                    ]
```

这种 Scavenger 思路不需要逐个整理大量死亡对象，只复制少量存活对象，因此适合新生代。

它的代价是需要预留复制空间，而且存活率过高时复制成本会增加。

### 4.6 对象为什么会晋升到老生代

一个对象经过多轮 Minor GC 仍然存活，说明它可能不是短命临时值。继续每轮复制它并不划算，引擎会把它晋升到老生代。

另外，当目标复制空间压力较大或对象符合其他内部条件时，也可能发生晋升。

具体年龄和空间阈值属于 V8 实现细节，不适合死记。核心逻辑是：

```text
对象反复存活
→ 短期回收区不再适合它
→ 移入面向长期对象的老生代
```

### 4.7 老生代与 Major GC

老生代中大部分对象可能仍然存活。如果像新生代一样复制全部存活对象，成本会很高。

老生代通常采用标记清除和标记整理思路：1）**标记清除**：标记存活对象，回收死亡对象留下的空间； 2）**标记整理**：在必要时移动存活对象，把零散空洞合并成连续空间。

标记清除后可能形成碎片：

```text
[对象 A][空闲][对象 C][空闲][对象 E]
```

总空闲空间可能很多，但每一块都很小，无法放入一个大对象。标记整理后：

```text
[对象 A][对象 C][对象 E][连续空闲空间]
```

整理能解决碎片，但移动对象和修正所有相关引用需要额外成本，所以引擎会根据内存状态决定何时进行。

### 4.8 三色标记解决了什么表达问题

为了让标记过程可以暂停和继续，引擎通常用三色模型描述对象状态：1）**白色**：尚未发现，当前仍可能是垃圾； 2）**灰色**：对象已经发现，但它引用的子对象还没有全部检查； 3）**黑色**：对象和它的直接引用已经检查完成。

标记从根开始：

```text
初始：Root 为灰色，其他对象为白色
扫描 Root：Root 变黑，它引用的对象变灰
继续扫描灰色对象：发现更多可达对象
没有灰色对象后：剩余白色对象不可达
```

“颜色”只是算法状态，不是对象的真实属性。

### 4.9 为什么 GC 会暂停 JavaScript

如果 JavaScript 一边修改对象引用，GC 一边遍历对象图，GC 看到的关系可能不一致。

最简单、安全的做法是暂停 JavaScript，完成关键回收阶段后再恢复。这类暂停称为 Stop The World。

问题在于：如果堆很大，一次完整标记持续几十甚至几百毫秒，主线程无法执行事件回调和渲染，用户就会看到卡顿。

现代垃圾回收器会通过增量、并发和并行降低影响：1）**增量**：把一次大标记拆成多个小阶段，中间允许 JavaScript 继续运行； 2）**并发**：部分标记工作在后台线程进行，与 JavaScript 执行重叠； 3）**并行**：多个辅助线程共同完成一部分 GC 工作。

这些方法不能让 GC 变成零成本，只是减少主线程单次连续暂停。

### 4.10 增量标记为什么需要写屏障

假设 `A` 已经扫描完成并标为黑色，`B` 仍然是尚未发现的白色对象。JavaScript 在两段增量标记之间执行：

```js
A.child = B;
```

此时 `B` 已经变成可达对象，但 GC 可能认为 `A` 已经检查完，不再回头扫描。如果不记录这次变化，`B` 可能被错误回收。

写屏障的作用是：程序修改引用时，引擎记录可能影响标记正确性的关系，让 GC 重新检查或调整对象颜色。

```text
JavaScript 修改引用
→ 写屏障记录变化
→ GC 修正标记集合
→ 保证可达对象不会漏标
```

写屏障会带来少量额外开销，但换来了增量和并发回收的正确性。

### 4.11 老生代如何知道谁指向新生代

Minor GC 如果每次都扫描整个老生代，就失去了“小范围快速回收”的意义。

当老生代对象新增了指向新生代对象的引用时，写屏障可以把相关区域记录到 remembered set（记忆集）中：

```js
longLivedObject.child = newObject;
```

下一次 Minor GC 只需要检查根和这些被记录的老生代区域，就能找到被老对象引用的新对象，无需遍历整个老生代。

### 4.12 分配速率为什么会造成周期性卡顿

下面的代码每帧都会创建一批新对象：

```js
function update(points) {
  return points.map((point) => ({
    x: point.x * scale,
    y: point.y * scale
  }));
}
```

这些对象很快死亡，并不构成泄漏。但如果每秒创建数百万个对象，新生代会快速填满，Minor GC 就会频繁发生：

```text
高频创建临时对象
→ 新生代快速用满
→ Minor GC 频繁触发
→ 主线程周期性暂停
→ 动画出现规律性掉帧
```

这叫分配压力。它和内存泄漏的区别是：GC 后内存能够回落，只是回收过于频繁。

只有工具确认分配是瓶颈时，才值得考虑减少中间对象或复用缓冲区。普通业务代码偶尔创建对象，不需要为此牺牲清晰度。

### 4.13 断开引用不等于立即释放内存

```js
let data = new Array(1_000_000).fill('x');
data = null;
```

这段代码只断开变量 `data` 的引用。随后可能出现几种情况：1）如果没有其他引用，对象具备了被回收的条件； 2）GC 何时执行由引擎决定，不保证立即发生； 3）引擎回收对象后，可能保留已申请的堆空间以便复用； 4）操作系统看到的进程内存不一定马上下降。

所以不能通过“设为 `null` 后任务管理器内存没有立即减少”判断泄漏。正确方法是多轮复现、等待 GC，并查看存活对象和保留链。

### 4.14 GC 的完整面试回答

> JavaScript 引擎根据可达性回收对象，从 GC Root 出发标记所有能够到达的对象，未被标记的对象可以回收。V8 又根据大多数对象生命周期很短的规律进行分代：新对象进入新生代，Minor GC 通过复制少量存活对象快速回收；多轮存活的对象晋升到老生代，老生代主要使用标记清除和标记整理。为了降低长暂停，现代 GC 会使用增量、并发和并行技术，并通过写屏障保证 JavaScript 修改引用时标记仍然正确。频繁创建临时对象会提高 GC 频率，而无用对象仍然可达则会形成内存泄漏。

## 5. 内存泄漏

### 5.1 什么才叫内存泄漏

内存泄漏不是“页面使用了很多内存”，而是：

> 某些对象在业务上已经不再需要，但仍然能从 GC Root 到达，所以垃圾回收器无法回收它们。

下面三种情况必须区分：

#### 正常高内存

图片编辑器正在处理一张大型图片，确实需要几百 MB 内存。只要任务结束后相关对象能够释放，这不是泄漏。

#### 暂时增长

打开一个弹窗时创建数据，关闭后内存不会立刻下降，但下一次 GC 后能够回到接近原来的基线。这也不是泄漏。

#### 持续泄漏

每打开并关闭一次弹窗，都会残留一份数据。重复十次后残留十份，GC 后基线仍然持续上升，这才符合泄漏特征。

```text
正常：100MB → 150MB → GC → 105MB
泄漏：100MB → 150MB → GC → 130MB
                 再操作 → GC → 160MB
```

因此，不能用某一个时刻的内存截图判断泄漏，必须观察重复操作后的趋势。

### 5.2 全局引用为什么危险

全局对象通常与页面拥有相同生命周期。只要数据挂在全局对象上，就会一直可达：

```js
window.debugData = new Array(1_000_000).fill('x');
```

引用链非常直接：

```text
Window
→ debugData
→ 大数组
```

除非主动删除或替换这个引用，否则 GC 不能回收数组。

全局缓存也有同样问题：

```js
const pageCache = new Map();

function cachePage(url, page) {
  pageCache.set(url, page);
}
```

如果 URL 不断变化、Map 从不删除，缓存就会成为永久存储。缓存的本质是用内存换时间，因此必须同时设计失效策略：1）最大容量； 2）过期时间； 3）LRU 淘汰； 4）用户退出或路由销毁时清空。

### 5.3 闭包什么时候变成问题

闭包本身不是泄漏。只要返回函数仍然有用，它捕获状态就是合理的：

```js
function createCounter() {
  let count = 0;
  return () => ++count;
}
```

问题出现在：长期存活的函数无意中捕获了大型对象。

```js
function createHandler() {
  const largeData = new Array(1_000_000).fill('x');

  return function handleClick() {
    console.log(largeData.length);
  };
}

window.handler = createHandler();
```

引用链是：

```text
Window
→ handler
→ 闭包环境
→ largeData
```

只要 `window.handler` 存在，数组就合理地被认为可达。

解决方法不是“不要用闭包”，而是缩小捕获内容或缩短函数生命周期。例如函数只需要数组长度，就不必捕获整个数组：

```js
function createHandler() {
  const largeData = new Array(1_000_000).fill('x');
  const length = largeData.length;

  return function handleClick() {
    console.log(length);
  };
}
```

实际引擎可能优化闭包环境，但业务设计仍应避免长期对象无意义地持有大数据。

### 5.4 定时器如何保留对象

```js
function mountPage() {
  const pageData = new Array(100_000).fill('data');

  setInterval(() => {
    console.log(pageData.length);
  }, 1000);
}

mountPage();
```

即使页面组件在视觉上已经移除，定时器仍注册在浏览器中：

```text
浏览器定时器系统
→ interval 回调
→ 闭包环境
→ pageData
```

正确设计是让创建资源的代码同时提供销毁方式：

```js
function mountPage() {
  const pageData = new Array(100_000).fill('data');

  const timerId = setInterval(() => {
    console.log(pageData.length);
  }, 1000);

  return function unmountPage() {
    clearInterval(timerId);
  };
}

const unmountPage = mountPage();

// 页面离开时
unmountPage();
```

清理定时器既释放引用，也避免已经无意义的后台计算继续消耗 CPU。

### 5.5 事件监听器为什么会泄漏组件状态

```js
function mountSearch(input) {
  const results = new Array(100_000).fill('result');

  input.addEventListener('input', () => {
    console.log(results.length);
  });
}
```

事件目标会保存监听函数，监听函数又通过闭包保存 `results`。如果组件多次挂载，每次都增加监听器，却从不清除，回调和数据就会不断累积。

保存同一个函数引用才能正确移除：

```js
function mountSearch(input) {
  const results = new Array(100_000).fill('result');

  function handleInput() {
    console.log(results.length);
  }

  input.addEventListener('input', handleInput);

  return function unmountSearch() {
    input.removeEventListener('input', handleInput);
  };
}
```

下面的写法无法移除原监听器，因为两次箭头函数是不同的函数对象：

```js
input.addEventListener('input', () => run());
input.removeEventListener('input', () => run());
```

### 5.6 用 AbortController 统一清理监听器

一个组件可能注册多个监听器。可以让它们共用同一个信号：

```js
function mountPage() {
  const controller = new AbortController();
  const { signal } = controller;

  window.addEventListener('resize', handleResize, { signal });
  document.addEventListener('visibilitychange', handleVisibility, {
    signal
  });

  return function unmountPage() {
    controller.abort();
  };
}
```

调用 `abort()` 后，使用该信号注册的监听器会被移除。它把多个资源的生命周期归到同一个组件清理动作中。

### 5.7 Observer 也属于需要释放的外部注册

`MutationObserver`、`ResizeObserver` 和 `IntersectionObserver` 会保存回调和观察目标：

```js
const observer = new ResizeObserver((entries) => {
  updateLayout(entries);
});

observer.observe(panel);
```

组件销毁时应解除观察：

```js
observer.unobserve(panel);
observer.disconnect();
```

如果继续观察已经失效的组件，不仅可能保留内存，还会在尺寸或 DOM 变化时执行无意义的回调。

### 5.8 游离 DOM 为什么仍然存在

把节点从页面移除，只断开了 DOM 树对它的引用：

```js
const panel = document.querySelector('.panel');
panel.remove();
```

变量 `panel` 仍然指向节点，所以节点依旧可达：

```text
JavaScript 变量 panel
→ 已从文档移除的 DOM 节点
→ 节点的子树
```

这种不在文档中、但仍被 JavaScript 引用的节点常被称为 Detached DOM。

这不一定是泄漏：代码可能准备稍后把节点重新插入页面。只有当节点已经永久失效，却被全局数组、缓存、监听器或闭包长期保留时，才构成问题。

### 5.9 异步请求与失效页面

请求最终完成后，相关对象通常可以释放，因此未取消请求不必然造成永久泄漏。但页面离开后，回调仍可能持有旧状态并执行无意义工作：

```js
async function loadUser() {
  const response = await fetch('/api/user');
  const user = await response.json();
  renderUser(user);
}
```

如果页面已经卸载，`renderUser` 可能修改失效 DOM，或者旧请求晚于新请求返回，覆盖新状态。

可以把请求生命周期与页面绑定：

```js
function loadUser() {
  const controller = new AbortController();

  fetch('/api/user', { signal: controller.signal })
    .then((response) => response.json())
    .then(renderUser)
    .catch((error) => {
      if (error.name !== 'AbortError') {
        reportError(error);
      }
    });

  return () => controller.abort();
}
```

取消请求同时减少无效网络、回调和竞态问题。

### 5.10 WeakMap 为什么能避免额外保活

普通 Map 会强引用键：

```js
const metadata = new Map();

function attachMetadata(element, value) {
  metadata.set(element, value);
}
```

引用链是：

```text
全局 metadata
→ Map 的键 element
→ DOM 节点
```

即使 DOM 已经从页面删除，只要 Map 条目存在，节点仍可达。

如果元数据只应该跟随节点生命周期，可以使用 WeakMap：

```js
const metadata = new WeakMap();

function attachMetadata(element, value) {
  metadata.set(element, value);
}
```

WeakMap 对键的引用不会单独阻止键对象被回收。当其他强引用都消失后，节点和对应条目可以一起消失。

WeakMap 不能枚举键。原因是 GC 时机不确定：如果允许枚举，程序观察到的键集合会随着不可预测的回收时机变化。

WeakMap 适合“附属数据跟随对象一起生灭”，不适合需要遍历、统计大小或按字符串键缓存的场景。

### 5.11 WeakRef 和 FinalizationRegistry 为什么不能用于关键逻辑

`WeakRef` 允许弱引用对象：

```js
let target = { data: 'value' };
const reference = new WeakRef(target);

target = null;

const value = reference.deref();
if (value) {
  console.log(value.data);
}
```

`deref()` 可能得到对象，也可能得到 `undefined`，因为引擎可能已经回收对象。

`FinalizationRegistry` 可以在对象回收后安排回调：

```js
const registry = new FinalizationRegistry((label) => {
  console.log(`${label} 已被回收`);
});

let target = {};
registry.register(target, 'target');
target = null;
```

但它们不能承担关键资源释放：1）GC 何时发生不确定； 2）回调何时执行不确定； 3）页面关闭前可能根本不执行； 4）程序不能依赖对象在某个时刻一定消失。

文件、锁、网络连接等资源应该通过显式生命周期管理释放，而不是等待 FinalizationRegistry。

### 5.12 一个有上限的 LRU 缓存

缓存必须有边界。下面用 Map 的插入顺序实现一个简化 LRU：

```js
class LRUCache {
  constructor(limit = 100) {
    this.limit = limit;
    this.map = new Map();
  }

  get(key) {
    if (!this.map.has(key)) return undefined;

    const value = this.map.get(key);
    this.map.delete(key);
    this.map.set(key, value);
    return value;
  }

  set(key, value) {
    if (this.map.has(key)) {
      this.map.delete(key);
    }

    this.map.set(key, value);

    if (this.map.size > this.limit) {
      const oldestKey = this.map.keys().next().value;
      this.map.delete(oldestKey);
    }
  }
}
```

最近访问的条目被移动到 Map 末尾，超过容量时删除最早的条目。

生产缓存还需要考虑过期时间、单个值大小、错误是否缓存以及并发请求合并。LRU 只解决容量淘汰，不解决所有缓存问题。

### 5.13 内存泄漏的排查步骤

以“打开并关闭弹窗”为例：1）在初始页面获取第一份 Heap Snapshot； 2）打开并关闭弹窗十次； 3）回到与初始相同的页面状态； 4）等待或触发 GC，再获取第二份快照； 5）再重复一轮，获取第三份快照； 6）比较持续增长的对象类型和 Detached DOM； 7）选择可疑对象，沿 Retainers 查找到 GC Root 的路径。

为什么要重复多轮？第一次增长可能只是模块初始化、字体缓存或框架预热。真正的泄漏通常会随着同一操作重复而持续积累。

如果保留链显示：

```text
Window
→ resize 监听器
→ handleResize 闭包
→ modalState
→ detached DOM
```

真正的修复是组件销毁时移除 `resize` 监听器，而不是单独把某个 DOM 变量赋值为 `null`。

### 5.14 内存泄漏的面试回答

> 内存泄漏指对象在业务上已经失效，但仍能从 GC Root 到达，因此无法被垃圾回收。常见根因包括全局缓存无上限、闭包无意持有大对象、定时器和监听器未清理、Observer 未断开，以及 Detached DOM 仍被 JavaScript 引用。排查时不能只看一次内存大小，而要重复相同操作、等待 GC、比较多份 Heap Snapshot，再沿 Retainer Chain 找到真正的持有者。修复后用相同操作验证对象数量和内存基线不再持续增长。

## 6. 事件循环与主线程性能

### 6.1 事件循环解决的是什么问题

JavaScript 在主线程上一次只能执行一段代码，但浏览器同时会发生许多事情：1）用户点击和输入； 2）定时器到期； 3）网络响应完成； 4）页面需要渲染下一帧。

这些事件不能随时插入正在执行的 JavaScript。浏览器把可执行工作组织成任务，事件循环在主线程空闲时依次处理。

一轮简化流程是：

```text
取出一个任务
→ 执行任务中的 JavaScript，直到调用栈为空
→ 清空微任务队列
→ 浏览器判断是否需要渲染
→ 进入下一轮事件循环
```

“执行到调用栈为空”很关键。一个任务开始后，浏览器不会因为用户点击或页面需要绘制，就随意打断普通 JavaScript。

### 6.2 任务为什么会阻塞输入

```js
button.addEventListener('click', () => {
  const start = performance.now();

  while (performance.now() - start < 300) {
    // 模拟重计算
  }
});
```

点击后，这个回调连续占用主线程约 300ms。在此期间：1）新的点击只能等待； 2）输入框无法及时响应； 3）动画回调不能执行； 4）浏览器无法及时生成下一帧。

用户看到的不是“计算很慢”这个抽象概念，而是页面冻结。

### 6.3 什么是 Long Task

在 Web 性能语境中，主线程连续执行超过 50ms 的任务通常会被视为 Long Task。

50ms 不是“超过就一定肉眼卡顿”的绝对物理边界，而是用来识别可能损害响应性的任务。

假设一个任务执行 120ms：

```text
任务总时间：120ms
前 50ms：任务正常执行区间
剩余 70ms：可能阻塞其他工作的时间
```

实验室指标 TBT 会把超过 50ms 的部分计入阻塞时间。

长任务可能来自：1）大型循环或复杂算法； 2）解析和执行大体积脚本； 3）框架一次更新大量组件； 4）大量 DOM 创建和布局； 5）垃圾回收暂停。

### 6.4 微任务为什么可能让页面无法渲染

Promise 回调和 `queueMicrotask` 会创建微任务。当前任务结束后，浏览器会在进入下一任务或渲染机会前清空微任务队列。

```js
console.log('task start');

Promise.resolve().then(() => {
  console.log('microtask');
});

console.log('task end');
```

输出：

```text
task start
task end
microtask
```

微任务执行期间还能继续创建微任务：

```js
function loop() {
  queueMicrotask(loop);
}

loop();
```

队列永远清不空，浏览器可能长期无法进入下一任务和渲染阶段。这叫微任务饥饿。

所以“微任务优先级更高”不等于“把工作放进 Promise 性能更好”。大量计算从普通代码搬到微任务，仍然占用主线程，甚至更容易阻止浏览器让出渲染机会。

### 6.5 一次渲染不是每轮事件循环必然发生

浏览器会根据刷新时机、页面状态和是否存在视觉变化判断是否渲染。下面是帮助理解的近似顺序：

```text
一个任务
→ 所有微任务
→ 可能执行 requestAnimationFrame 回调
→ 样式、布局、绘制
→ 下一任务
```

这不是要求死背的规范步骤表，而是说明两个性能事实：1）长任务结束前通常不会出现新的页面画面； 2）微任务队列长期不清空，也会推迟渲染。

### 6.6 为什么拆分任务能改善响应性

假设一次处理十万条数据：

```js
function processAll(items) {
  for (const item of items) {
    expensiveWork(item);
  }
}
```

如果整个循环需要 500ms，它会形成一个 500ms 长任务。

可以按照时间预算分批处理：

```js
function processInChunks(items, onComplete) {
  let index = 0;

  function runChunk() {
    const start = performance.now();

    while (index < items.length && performance.now() - start < 8) {
      expensiveWork(items[index]);
      index += 1;
    }

    if (index < items.length) {
      setTimeout(runChunk, 0);
    } else {
      onComplete?.();
    }
  }

  runChunk();
}
```

每批只连续执行大约 8ms，然后通过新的任务继续：

```text
处理一批
→ 当前任务结束
→ 浏览器有机会处理输入和渲染
→ 下一批进入新任务
```

拆分没有减少总计算量，甚至会增加调度成本。它改善的是响应性：用户不必连续 500ms 得不到反馈。

`8ms` 也不是通用最佳值。批次大小要根据设备、工作类型和交互要求测量。

### 6.7 拆分任务需要处理取消

如果用户已经离开页面，旧任务就没有继续执行的意义：

```js
function processInChunks(items, signal) {
  let index = 0;

  function runChunk() {
    if (signal.aborted) return;

    const start = performance.now();

    while (
      index < items.length &&
      !signal.aborted &&
      performance.now() - start < 8
    ) {
      expensiveWork(items[index]);
      index += 1;
    }

    if (index < items.length && !signal.aborted) {
      setTimeout(runChunk, 0);
    }
  }

  runChunk();
}

const controller = new AbortController();
processInChunks(items, controller.signal);

// 页面离开时
controller.abort();
```

异步分片让程序更易响应，也让状态管理更复杂：每批之间数据可能变化，因此要设计进度、取消、异常和一致性。

### 6.8 不同工作应该用不同调度时机

| 工作类型 | 用户要求 | 合适思路 |
|----------|----------|----------|
| 点击后的视觉反馈 | 立即看到结果 | 回调保持很小，优先完成关键更新 |
| 动画状态更新 | 下一帧前完成 | `requestAnimationFrame` |
| 大量可拆计算 | 允许分批完成 | 多任务分片，批次之间让出主线程 |
| 低优先级预计算 | 不紧急 | 空闲或低优先级调度 |
| 独立 CPU 密集计算 | 不能阻塞主线程 | Web Worker |

`requestIdleCallback` 会在浏览器认为存在空闲时间时执行回调：

```js
requestIdleCallback((deadline) => {
  while (tasks.length > 0 && deadline.timeRemaining() > 0) {
    run(tasks.shift());
  }
});
```

它适合低优先级工作，不适合必须在固定时间内完成的任务。繁忙页面可能很久没有空闲，后台页面也可能被限速。

支持任务优先级的调度 API 可以更明确地表达意图，但兼容性会变化。真正要掌握的是：先区分任务的紧急程度，再决定什么时候执行，而不是把所有工作都立刻塞进主线程。

### 6.9 Web Worker 为什么能保持页面响应

Worker 在独立线程执行 JavaScript。主线程发送数据，Worker 计算完成后再发回结果：

主线程：

```js
const worker = new Worker('./worker.js', { type: 'module' });

worker.postMessage({ numbers: [1, 2, 3, 4] });

worker.addEventListener('message', (event) => {
  result.textContent = event.data;
});
```

Worker：

```js
self.addEventListener('message', (event) => {
  const total = event.data.numbers.reduce((sum, value) => {
    return sum + value;
  }, 0);

  self.postMessage(total);
});
```

计算从主线程移开以后，页面仍能响应输入和渲染。但 CPU 工作并没有消失：

```text
主线程计算：阻塞页面，但没有通信成本
Worker 计算：页面保持响应，但增加线程启动和通信成本
```

Worker 适合计算量足够大、可以独立完成、不需要直接操作 DOM 的任务，例如图片处理、数据解析和复杂算法。

短小任务放进 Worker，通信成本可能比计算本身更高。

### 6.10 结构化克隆与 Transferable

向 Worker 发送普通对象时，浏览器通常通过结构化克隆创建一份独立数据。发送几 MB 或几十 MB 数据时，复制也会消耗 CPU 和内存。

`ArrayBuffer` 等可转移对象可以转移所有权：

```js
const buffer = new ArrayBuffer(1024 * 1024);

worker.postMessage(buffer, [buffer]);

console.log(buffer.byteLength); // 转移后通常为 0
```

底层数据不再复制，但主线程失去了该缓冲区的所有权。Transferable 解决的是大块二进制数据的传输成本，不是让任意对象共享内存。

### 6.11 事件委托为什么能减少大量监听器

为一万个列表项分别注册监听器：

```js
for (const item of list.children) {
  item.addEventListener('click', handleItemClick);
}
```

可以利用事件冒泡，只在父元素注册一次：

```js
list.addEventListener('click', (event) => {
  const item = event.target.closest('[data-item-id]');

  if (!item || !list.contains(item)) return;

  handleItem(item.dataset.itemId);
});
```

它减少了监听器数量，也能自动处理后来新增的列表项。

事件委托不是永远更快：它需要在父级判断目标，不可冒泡事件也不能直接使用。它适合大量同类子节点，而不是要求所有事件都统一放到 document。

### 6.12 主线程性能的面试回答

> 浏览器主线程同时负责执行 JavaScript、处理输入以及参与样式、布局和绘制。事件循环每次取出一个任务执行，任务结束后清空微任务，再获得可能的渲染机会。普通 JavaScript 任务不会被输入或渲染自动打断，因此长任务会造成输入延迟和掉帧；持续产生微任务也可能推迟渲染。优化时可以先减少工作量，再根据任务性质进行分片、用 requestAnimationFrame 对齐动画，或把独立的 CPU 密集计算移到 Worker。拆分和 Worker 改善的是主线程响应性，并不会让总计算量消失。

## 7. 浏览器渲染性能

### 7.1 从 DOM 修改到屏幕像素

当 JavaScript 修改页面时，浏览器可能经历以下阶段：

```text
JavaScript 修改 DOM 或样式
→ Style：计算元素最终样式
→ Layout：计算元素尺寸和位置
→ Paint：生成绘制指令
→ Composite：组合图层并显示
```

并不是每次修改都一定完整经过所有阶段。具体取决于修改了什么：1）修改宽高可能影响其他元素位置，需要 Layout； 2）修改背景色通常不改变几何信息，可能只需要 Paint； 3）修改已独立合成元素的 `transform`，可能主要发生在 Composite。

优化的关键是识别代码触发了流水线的哪些部分，而不是只背“重排比重绘慢”。

### 7.2 Style：确定元素最终样式

浏览器结合 CSS 规则、继承、层叠和元素状态，计算每个元素的最终样式。

```js
element.classList.add('active');
```

添加 class 后，浏览器需要判断哪些 CSS 规则发生变化。影响范围取决于选择器、DOM 关系和属性。

现代浏览器会进行样式失效范围优化，不是修改一个 class 就必然重新计算整个页面。但 DOM 规模越大、变化范围越广，样式计算成本越可能增加。

### 7.3 Layout：计算几何位置

布局阶段计算元素的：1）宽度和高度； 2）坐标位置； 3）与父子元素、相邻元素的几何关系。

修改一个元素的宽度可能影响父容器、兄弟节点甚至更大区域：

```js
sidebar.style.width = '300px';
```

布局成本不仅取决于修改次数，还取决于影响范围和 DOM 复杂度。

### 7.4 Paint 与 Composite

布局确定几何信息后，绘制阶段生成背景、文本、边框、阴影等绘制指令。

合成阶段把不同图层组合成最终画面。某些属性变化不需要重新布局和绘制，只需要更新图层位置或透明度：

```css
.moving {
  transform: translateX(100px);
  opacity: 0.8;
}
```

这就是动画通常优先考虑 `transform` 和 `opacity` 的原因：它们更有机会避免昂贵的 Layout 和 Paint。

“更有机会”不是绝对保证，浏览器仍会根据图层和页面状态决定实际路径。

### 7.5 一帧为什么只有约 16.7ms

60Hz 屏幕每秒刷新 60 次：

```text
1000ms ÷ 60 ≈ 16.7ms
```

如果页面希望每次刷新都提供新画面，就要在约 16.7ms 内完成一帧相关工作。

这段时间不全属于 JavaScript，还包括：1）事件处理； 2）样式计算； 3）布局； 4）绘制； 5）合成和浏览器内部工作。

如果 JavaScript 自己就运行 20ms，浏览器几乎不可能在同一帧内完成剩余工作，结果就是掉帧。

高刷新率屏幕的时间预算更短，例如 120Hz 一帧约 8.3ms。

### 7.6 强制同步布局是怎样产生的

浏览器会尝试批量处理 DOM 修改，而不是每写一次样式就立刻布局：

```js
box.style.width = '100px';
box.style.height = '100px';
box.classList.add('active');
```

这些写操作可以先记录下来，在合适的渲染阶段统一处理。

但如果写入后立即读取布局信息：

```js
box.style.width = '100px';
console.log(box.offsetWidth);
```

`offsetWidth` 必须返回最新结果。浏览器不能拿旧布局欺骗 JavaScript，只能提前完成样式和布局计算：

```text
修改样式
→ 旧布局失效
→ JavaScript 立即读取几何信息
→ 浏览器被迫同步执行 Layout
→ 返回最新值
```

这叫强制同步布局 Forced Synchronous Layout。

### 7.7 Layout Thrashing 为什么昂贵

如果在循环中反复读写：

```js
for (const card of cards) {
  const width = container.offsetWidth;
  card.style.width = `${width / 3}px`;
}
```

第一轮写入可能让布局失效，下一轮读取又要求最新布局，于是形成：

```text
读布局 → 写样式 → 读布局 → 写样式 → 读布局 → 写样式
```

这种反复强制布局叫 Layout Thrashing。

如果容器宽度在循环中不变，只读取一次：

```js
const width = container.offsetWidth;
const cardWidth = width / 3;

for (const card of cards) {
  card.style.width = `${cardWidth}px`;
}
```

现在顺序变成：

```text
集中读取
→ JavaScript 计算
→ 集中写入
```

这不仅减少 JavaScript 调用次数，更重要的是避免浏览器在循环中反复刷新布局。

### 7.8 requestAnimationFrame 为什么适合动画

`requestAnimationFrame` 告诉浏览器：这段回调用于准备下一帧画面。

```js
const start = performance.now();
const duration = 300;

function animate(now) {
  const progress = Math.min((now - start) / duration, 1);

  element.style.transform = `translateX(${progress * 200}px)`;

  if (progress < 1) {
    requestAnimationFrame(animate);
  }
}

requestAnimationFrame(animate);
```

这段代码根据真实时间计算进度。即使某一帧错过，动画总持续时间仍接近 300ms。

如果写成“每帧移动 5px”，帧率降低时动画就会变慢。

与 `setInterval(fn, 16)` 相比，`requestAnimationFrame` 还有两个优势：1）与浏览器渲染节奏对齐； 2）页面不可见时通常会暂停或降低频率，避免无意义工作。

但如果回调本身需要 50ms，换成 `requestAnimationFrame` 仍然会掉帧。它解决调度时机，不解决工作量。

### 7.9 图层提升不是免费的

浏览器可能把某些元素放进独立合成层，使它们移动时不必重绘其他内容。

可以使用 `will-change` 提示即将变化：

```css
.moving-element {
  will-change: transform;
}
```

独立图层也有成本：1）占用额外内存； 2）创建和上传纹理需要时间； 3）图层越多，合成管理越复杂。

因此不能给所有元素添加 `will-change`。它应该用于少量、确实即将频繁变化的元素，并在不需要时移除。

### 7.10 CSS Containment 如何缩小影响范围

如果一个组件的内部布局不应影响外部，可以使用 containment 向浏览器提供边界信息：

```css
.widget {
  contain: layout paint;
}
```

浏览器可以在某些情况下把布局和绘制影响限制在组件区域内。

`content-visibility` 可以跳过当前不可见区域的部分渲染：

```css
.article-section {
  content-visibility: auto;
  contain-intrinsic-size: 500px;
}
```

`contain-intrinsic-size` 为尚未渲染的区域提供预估尺寸，减少滚动到该区域时的布局跳变。

这些属性会改变布局和包含关系，必须检查实际视觉效果。它们减少渲染工作，不会自动减少数据请求或 JavaScript 计算。

### 7.11 为什么大量 DOM 会变慢

十万个列表项意味着浏览器要维护十万个节点及其样式、布局和事件相关状态：

```js
for (const item of items) {
  const element = document.createElement('li');
  element.textContent = item.name;
  list.appendChild(element);
}
```

成本包括：1）创建节点和 JavaScript 对象； 2）将节点加入 DOM； 3）计算样式和布局； 4）占用内存； 5）后续更新和查询更昂贵。

使用 `DocumentFragment` 可以避免逐个插入时暴露中间状态：

```js
const fragment = document.createDocumentFragment();

for (const item of items) {
  const element = document.createElement('li');
  element.textContent = item.name;
  fragment.appendChild(element);
}

list.appendChild(fragment);
```

但最终仍然创建了十万个节点。它不能解决 DOM 总量本身过大的问题。

### 7.12 虚拟列表如何减少 DOM 总量

虚拟列表只渲染视口附近的数据：

```text
数据：100000 条
视口实际只能看到：20 条
加上缓冲区实际渲染：约 30～50 条
```

定高列表可以根据滚动位置计算起始索引：

```js
const startIndex = Math.floor(scrollTop / itemHeight);
const visibleCount = Math.ceil(viewportHeight / itemHeight);
const endIndex = startIndex + visibleCount + overscan;

const visibleItems = items.slice(startIndex, endIndex);
```

容器仍然保留完整列表对应的总高度，让滚动条长度正确；可见元素通过偏移放到正确位置。

虚拟列表把成本从“与全部数据量相关”变成“主要与可见数量相关”。

它也会引入复杂度：1）不定高元素需要测量和缓存高度； 2）快速滚动可能出现短暂空白； 3）DOM 复用要正确处理组件状态； 4）焦点、键盘导航和可访问性更难实现。

所以少量数据不需要虚拟化，只有 DOM 总量成为实际瓶颈时才值得使用。

### 7.13 渲染性能的面试回答

> 浏览器把页面更新分成样式计算、布局、绘制和合成。改变尺寸和位置通常会触发布局，改变颜色通常需要绘制，而 transform 和 opacity 更有机会只参与合成。JavaScript 写入样式后立即读取 offsetWidth 等几何属性，会迫使浏览器提前完成布局；如果循环中反复读写，就形成 Layout Thrashing。优化时应集中读取、集中写入，动画使用 requestAnimationFrame 对齐帧，并通过虚拟列表减少大型列表的 DOM 总量。所有优化最终都要在 Performance 面板中确认实际减少了 Layout、Paint 或主线程时间。

## 8. 性能优化的方法论

### 8.1 性能优化的第一步是定义问题

“页面有点慢”无法直接指导优化。必须把它转换成可以观察的现象：1）首屏主要内容需要 5 秒才出现； 2）点击按钮后 400ms 才显示反馈； 3）滚动列表时每隔一段时间明显卡顿； 4）页面反复切换后内存从 100MB 增长到 500MB。

不同现象对应不同证据和工具：

| 现象 | 首先检查 |
|------|----------|
| 首屏慢 | 网络瀑布、LCP、脚本解析和主线程 |
| 点击响应慢 | 交互时间线、长任务、INP |
| 动画掉帧 | Frames、JavaScript、Layout、Paint |
| 内存增长 | Heap Snapshot、Allocation、Retainers |

只有先定义问题，才能判断优化是否成功。

### 8.2 优先减少工作量

假设每次搜索都遍历十万条数据。把循环语法从 `forEach` 改成 `for` 可能只有微小差异；如果先把候选数据缩小到一千条，工作量会直接降低两个数量级。

优化优先级通常是：

```text
不做无意义的工作
→ 减少数据规模和执行次数
→ 改进算法与数据结构
→ 改变调度方式
→ 最后考虑底层微优化
```

例如判断某个 ID 是否存在：

```js
// 每次查询都线性扫描
const exists = list.some((item) => item.id === targetId);
```

如果要重复查询很多次，可以预先构建 Set：

```js
const idSet = new Set(list.map((item) => item.id));
const exists = idSet.has(targetId);
```

构建 Set 本身也有时间和内存成本。只查一次时，直接扫描可能更合适；重复查询很多次时，索引才值得建立。

### 8.3 防抖为什么适合“只关心最终输入”

用户输入 `javascript` 会触发十次左右 `input` 事件。如果每次都立即请求，前面的中间结果通常没有价值。

防抖会在事件停止一段时间后执行：

```js
function debounce(fn, delay) {
  let timerId;

  return function (...args) {
    clearTimeout(timerId);

    timerId = setTimeout(() => {
      fn.apply(this, args);
    }, delay);
  };
}

const search = debounce((keyword) => {
  fetchSearchResult(keyword);
}, 200);

input.addEventListener('input', (event) => {
  search(event.target.value);
});
```

连续输入时旧定时器不断取消，只有停止约 200ms 后才真正搜索。

代价是结果会额外延迟 200ms。延迟太大会让界面显得迟钝，因此需要根据交互体验选择。

### 8.4 节流为什么适合“持续过程仍需反馈”

滚动时可能每秒产生几十次事件。页面需要持续更新位置，但不需要处理每一次事件。

```js
function throttle(fn, interval) {
  let lastTime = 0;

  return function (...args) {
    const now = performance.now();

    if (now - lastTime >= interval) {
      lastTime = now;
      fn.apply(this, args);
    }
  };
}

window.addEventListener('scroll', throttle(() => {
  updateScrollProgress(window.scrollY);
}, 100));
```

节流保证单位时间内最多执行一定次数，适合滚动进度、拖拽采样等需要中间反馈的场景。

防抖和节流都只减少执行次数。如果单次回调仍需 500ms，它们不能解决回调本身过重的问题。

### 8.5 缓存为什么既能优化也能制造问题

缓存用内存保存计算结果，避免下次重复计算：

```js
function memoize(fn) {
  const cache = new Map();

  return function (key) {
    if (cache.has(key)) {
      return cache.get(key);
    }

    const value = fn(key);
    cache.set(key, value);
    return value;
  };
}
```

它有效的前提是：1）同一个 key 会被重复访问； 2）原计算确实昂贵； 3）结果在缓存期间保持有效； 4）key 数量受到控制。

如果每次 key 都不同，缓存几乎没有命中，却会不断占用内存。缓存设计必须同时回答：

```text
什么时候写入？
什么时候失效？
最多保存多少？
如何处理错误结果？
```

### 8.6 代码分割为什么能改善启动性能

一个大型应用如果把所有路由代码打进首屏脚本，浏览器需要下载、解析和编译大量暂时用不到的代码。

动态导入可以把低频功能推迟到真正需要时：

```js
button.addEventListener('click', async () => {
  const { openEditor } = await import('./heavy-editor.js');
  openEditor();
});
```

收益是首屏工作减少；代价是用户第一次打开编辑器时需要等待网络和模块初始化。

可以根据使用概率选择预加载或预取，但不能把所有模块都提前加载，否则又失去分割意义。

### 8.7 Worker、分片和直接执行怎么选择

```text
任务很小
→ 直接执行，避免额外复杂度

任务较大但可以分批，且每批需要访问页面状态
→ 主线程分片

任务计算密集、可以独立完成、不依赖 DOM
→ Worker
```

Worker 不是“更快线程”的同义词。设备总 CPU 工作不会减少，并且会增加通信和数据传输。它的主要价值是把计算从页面主线程移开。

### 8.8 优化必须用相同场景验证

假设优化前点击耗时 300ms，优化后本地测试只需 120ms。还需要确认：1）使用的是相同数据量； 2）浏览器和设备条件相同； 3）没有因为缓存预热造成假象； 4）功能结果一致； 5）没把成本转移到内存或后续任务； 6）多次测试结果稳定。

性能优化是实验过程：提出假设、修改一个关键因素、重新测量。一次同时改十处，很难判断真正生效的是哪一处。

### 8.9 不要迷信微型 Benchmark

下面的测试看似简单：

```js
const start = performance.now();

for (let i = 0; i < 1_000_000; i += 1) {
  test();
}

console.log(performance.now() - start);
```

结果可能受到以下因素影响：1）JIT 是否已经预热； 2）测试中是否发生 GC； 3）引擎是否消除了无用结果； 4）设备温度和后台任务； 5）测试数据是否符合真实业务。

微型基准可以帮助研究局部行为，但不能替代真实页面、真实数据和用户操作下的测量。

## 9. 使用 DevTools 定位性能问题

### 9.1 Performance 面板应该从全局看起

标准流程是：1）开始录制； 2）只执行一次明确、可复现的用户操作； 3）停止录制； 4）先看时间线上的长任务、帧率和交互位置； 5）再展开 Main Thread 判断时间花在 JavaScript、Layout 还是 Paint； 6）最后进入具体函数和调用栈。

不要一开始就在几千个函数中搜索“看起来可疑”的名字。性能问题首先是时间线问题：用户卡顿发生在什么时候，那段时间主线程在做什么。

### 9.2 火焰图怎样阅读

火焰图横向表示时间，纵向表示调用关系：

```text
handleClick ──────────────────────
  filterData ─────────────
    normalize ───────
  renderList ───────────────
```

1）一个块越宽，表示它覆盖的时间越长； 2）上层块调用下层块； 3）父函数总时间包含子函数时间； 4）Self Time 是函数自身代码消耗，不包含子调用； 5）Total Time 是函数连同所有子调用的总消耗。
如果 `handleClick` 很宽，但 Self Time 很小，说明真正成本在它调用的函数中。

### 9.3 Bottom-Up 与 Call Tree 的区别

Bottom-Up 按函数累计耗时聚合，适合回答：

> 整段录制中，哪个函数总共最耗时？

Call Tree 保留调用结构，适合回答：

> 这个昂贵函数是从哪条业务路径调用进来的？

同一个工具函数可能被多个模块调用。Bottom-Up 找到它以后，还要通过调用树确认究竟是哪条业务路径造成问题。

### 9.4 如何识别强制布局

Performance 记录中如果 JavaScript 调用栈下出现同步的 Recalculate Style 或 Layout，并伴随 Forced reflow 警告，说明脚本读取了必须依赖最新布局的数据。

排查时沿调用栈寻找：1）`offsetWidth`、`offsetHeight`； 2）`clientWidth`、`clientHeight`； 3）`scrollTop` 等布局相关属性； 4）`getBoundingClientRect()`； 5）某些计算样式读取。

这些 API 本身不是错误。问题是它们是否出现在样式写入之后，尤其是否位于高频循环中。

### 9.5 Heap Snapshot 回答“谁还活着”

Heap Snapshot 是某一时刻堆对象关系的快照。常见字段：1）**Shallow Size**：对象自身直接占用的空间； 2）**Retained Size**：如果该对象被回收，连带可能释放的总空间； 3）**Retainers**：谁直接或间接持有该对象。

一个对象自身可能很小，却持有一棵巨大的对象图：

```text
小型 PageController
→ 大型数据数组
→ DOM 子树
```

PageController 的 Shallow Size 很小，Retained Size 却可能很大。

### 9.6 比较多份快照

以弹窗泄漏为例：1）初始页面获取 Snapshot A； 2）打开、关闭弹窗十次； 3）等待或触发 GC，获取 Snapshot B； 4）再重复十次，获取 Snapshot C； 5）在 Comparison 视图中查看持续增加的对象； 6）沿 Retainers 找到持有者。

只比较一前一后可能把正常的懒初始化误认为泄漏。连续多轮增长更有说服力。

### 9.7 Allocation 工具回答“对象在哪里创建”

不同工具回答不同问题：1）Heap Snapshot：当前有哪些存活对象，为什么仍然存活； 2）Allocation instrumentation on timeline：对象在什么时间创建，GC 后哪些还存活； 3）Allocation sampling：哪些调用栈累计分配了大量内存。

如果内存能回落，但 GC 过于频繁，应查找高分配热点；如果对象始终不消失，应查看快照和 Retainers。

### 9.8 用 Performance API 标记业务阶段

浏览器时间线能显示函数，但业务标记能说明“这一段在做搜索”：

```js
performance.mark('search-start');

const result = runSearch(data, keyword);

performance.mark('search-end');
performance.measure('search', 'search-start', 'search-end');

const [entry] = performance.getEntriesByName('search');
console.log(entry.duration);
```

测量短时间间隔时，`performance.now()` 比 `Date.now()` 更合适，因为它使用单调时间基准：

```js
const start = performance.now();
runTask();
const duration = performance.now() - start;
```

### 9.9 诊断必须形成证据链

一个合格结论不应该是“感觉循环太多”，而应该是：

```text
点击搜索后卡顿
→ Performance 显示 280ms 长任务
→ Bottom-Up 显示 normalize 占 170ms
→ normalize 对相同数据重复运行
→ 提前预处理并缓存规范化结果
→ 相同场景重新录制，任务降到 70ms
→ 搜索结果和内存占用仍然正确
```

只有现象、证据、原因、修改和验证全部连上，才完成一次性能优化。

### 9.10 测试环境会影响结果

1）开发模式可能包含额外检查和日志； 2）DevTools 本身会增加开销； 3）高性能电脑不能代表低端手机； 4）CPU 和网络节流只是模拟，不完全等于真实设备； 5）浏览器扩展和后台标签可能影响录制。
重要结论应在接近生产的构建、多个设备条件和多次录制中验证。

## 10. 性能指标与线上监控

### 10.1 指标必须对应用户感受

用户不关心函数执行了多少毫秒，他们关心三件事：

```text
什么时候能看到主要内容？
操作以后多久得到反馈？
页面会不会突然跳动？
```

Core Web Vitals 用三个指标分别描述这些体验：1）LCP：加载速度； 2）INP：交互响应； 3）CLS：视觉稳定性。

### 10.2 LCP：主要内容什么时候出现

LCP 是 Largest Contentful Paint，记录视口中主要内容元素完成绘制的时间。

如果首屏主体是一张大图，完整链路可能是：

```text
HTML 返回
→ 浏览器发现图片 URL
→ 发起图片请求
→ 图片下载和解码
→ 主线程完成必要布局
→ 图片绘制到屏幕
→ 形成 LCP
```

任何阶段过慢都会推迟 LCP：1）服务端响应慢，HTML 很晚才到； 2）图片 URL 藏在很晚执行的 JavaScript 中； 3）图片体积过大； 4）CSS 或 JavaScript 阻塞渲染； 5）主线程正被长任务占用，资源到了也无法及时绘制。

通常把 2.5 秒以内视为良好区间，并使用真实用户数据的第 75 百分位评价。

优化 LCP 不能只“压缩图片”，而要先确定耗时发生在资源发现、网络下载、元素渲染延迟还是主线程阻塞。

### 10.3 INP：一次交互为什么迟钝

INP 是 Interaction to Next Paint，用页面生命周期中具有代表性的高延迟交互评价整体响应能力。

一次交互从用户操作到画面更新，大致分成三段：

```text
输入延迟
→ 事件回调执行时间
→ 呈现延迟
```

#### 输入延迟

用户已经点击，但主线程正在执行其他长任务，回调无法开始。

#### 回调执行时间

事件处理器开始执行，但自身计算或组件更新过重。

#### 呈现延迟

回调结束后，浏览器还要处理微任务、样式、布局和绘制，下一帧才真正出现。

因此 INP 差不一定说明点击回调本身很慢，也可能是点击前已有长任务，或者回调后触发了昂贵布局。

通常把 200ms 以内视为良好区间，同样关注真实用户第 75 百分位。

### 10.4 CLS：页面为什么会突然跳动

CLS 是 Cumulative Layout Shift，衡量意外布局偏移的累计影响。

典型问题：图片加载前没有尺寸：

```html
<img src="banner.jpg" alt="banner">
```

图片下载前，浏览器不知道它占多高，下面的文字先出现在顶部；图片加载后突然撑开空间，文字向下跳。

预留尺寸：

```html
<img
  src="banner.jpg"
  alt="banner"
  width="1200"
  height="600"
>
```

浏览器可以提前根据宽高比保留位置。

其他常见原因：1）在已有内容上方异步插入广告； 2）Web Font 替换后文字尺寸变化； 3）动画通过修改 `top`、`height` 等属性推动周围内容； 4）异步组件没有稳定占位。

通常把 0.1 以内视为良好区间。

### 10.5 TBT 与 Long Task 的关系

TBT 是 Total Blocking Time，常用于实验室环境。它统计一定区间内，每个长任务超过 50ms 的部分。

一个 120ms 任务贡献：

```text
120ms - 50ms = 70ms Blocking Time
```

TBT 可以帮助发现页面加载期间主线程被阻塞的程度，但它不等于 INP：1）TBT 主要是实验室加载指标； 2）INP 关注真实交互到下一次绘制； 3）没有用户交互时，页面也可能存在很多长任务。

### 10.6 为什么 FPS 不能代表全部性能

FPS 适合观察动画和滚动是否流畅，但一个静态页面即使 FPS 正常，也可能：1）首屏等待 8 秒； 2）点击按钮 500ms 后才响应； 3）内存持续泄漏。

性能指标必须与具体体验对应，不能拿一个数字概括整个页面。

### 10.7 Lab Data 与真实用户数据

#### 实验室数据

在受控设备、网络和操作流程下测量，例如 Lighthouse 或本地 Performance 录制。

优点：1）容易重复； 2）适合定位和对比修改； 3）可以固定 CPU 和网络条件。

缺点：无法覆盖真实用户的设备、网络和使用路径。

#### 真实用户监控 RUM

在真实用户环境中采集性能数据。

优点：能看到低端设备、不同网络和真实交互造成的长尾问题。

缺点：数据噪声更大，还要处理采样、隐私和上报成本。

两者不是替代关系：线上数据告诉你“真实用户哪里有问题”，实验室工具帮助你“稳定复现并定位问题”。

### 10.8 为什么线上指标看第 75 百分位

假设十个用户中九个人响应时间是 100ms，一个低端设备用户是 2000ms。平均值是 290ms，既不能代表大多数人，也不清楚长尾有多严重。

分位数更适合描述体验分布。第 75 百分位表示至少 75% 的样本不超过这个值。

还应按维度拆分：1）移动端和桌面端； 2）页面或路由； 3）浏览器版本； 4）网络类型； 5）设备性能； 6）应用版本。

整体数据正常，可能只是高性能桌面用户掩盖了移动端问题。

### 10.9 使用 PerformanceObserver

`PerformanceObserver` 可以订阅浏览器提供的性能条目：

```js
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log({
      type: entry.entryType,
      name: entry.name,
      startTime: entry.startTime,
      duration: entry.duration
    });
  }
});

observer.observe({
  entryTypes: ['mark', 'measure']
});
```

浏览器支持的类型不同，可以查询：

```js
console.log(PerformanceObserver.supportedEntryTypes);
```

观察长任务：

```js
if (PerformanceObserver.supportedEntryTypes.includes('longtask')) {
  const longTaskObserver = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      reportLongTask({
        startTime: entry.startTime,
        duration: entry.duration
      });
    }
  });

  longTaskObserver.observe({
    type: 'longtask',
    buffered: true
  });
}
```

Core Web Vitals 的正式计算包含交互分组、会话窗口等规则。生产项目更适合使用经过维护的统计库，而不是根据单条 PerformanceEntry 自己拼出近似指标。

### 10.10 监控代码也要控制成本

性能监控本身运行在用户页面中，如果每次事件都发送请求，会制造新的性能问题。

常见控制方式：1）按用户或会话采样； 2）批量聚合后上报； 3）只记录慢于阈值的异常样本； 4）避免上报敏感业务数据； 5）给监控脚本设置体积和执行时间预算。

监控的目标是观察应用，而不是成为应用最重的部分。

## 11. 三个完整诊断案例

### 11.1 案例一：搜索输入时页面卡顿

问题代码：

```js
input.addEventListener('input', (event) => {
  const keyword = event.target.value.toLowerCase();

  const result = largeList.filter((item) => {
    return expensiveNormalize(item.name).includes(keyword);
  });

  renderList(result);
});
```

每输入一个字符，代码都会：1）遍历完整列表； 2）对每条名称重复执行昂贵规范化； 3）重新渲染全部结果。

Performance 录制可能显示一个与输入事件对应的长任务，Bottom-Up 中 `expensiveNormalize` 和 `renderList` 占据主要时间。

第一步不是加 Worker，而是减少重复工作。名称通常不会在每次输入时改变，可以提前处理：

```js
const searchableList = largeList.map((item) => ({
  item,
  normalizedName: expensiveNormalize(item.name)
}));
```

搜索时直接复用：

```js
function runSearch(keyword) {
  const normalizedKeyword = keyword.toLowerCase();

  return searchableList.filter((entry) => {
    return entry.normalizedName.includes(normalizedKeyword);
  });
}
```

如果只关心用户停止输入后的结果，再增加防抖，减少触发次数。结果过多时使用分页或虚拟列表，减少 DOM 数量。

优化顺序是：

```text
消除重复规范化
→ 减少搜索触发次数
→ 减少渲染数量
→ 仍然很重时再考虑分片或 Worker
```

最后在相同数据和输入内容下重新录制，确认输入任务变短、下一帧更快出现，同时结果仍然正确。

### 11.2 案例二：路由切换后内存持续上涨

现象是页面 A 和 B 之间反复切换，回到相同状态后内存基线仍不断升高。

排查过程：1）初始状态获取 Snapshot A； 2）A/B 切换十次，回到初始页面； 3）等待 GC，获取 Snapshot B； 4）再切换十次，获取 Snapshot C； 5）比较持续增长的页面实例和 Detached DOM； 6）查看可疑对象的 Retainers。

假设发现保留链：

```text
Window
→ resize 监听器
→ handleResize 闭包
→ pageState
→ 已删除的 DOM 子树
```

页面视觉上已经消失，但全局 `resize` 监听器仍然存在，监听器的闭包保存了整个页面状态。

修复为统一生命周期：

```js
function mountPage() {
  const controller = new AbortController();
  const timerId = setInterval(refresh, 5000);
  const observer = new ResizeObserver(handleResize);

  window.addEventListener('resize', handleResize, {
    signal: controller.signal
  });

  observer.observe(panel);

  return function unmountPage() {
    controller.abort();
    clearInterval(timerId);
    observer.disconnect();
  };
}
```

修复后重复相同轮次，页面实例数量不再线性增加，Detached DOM 能在 GC 后消失，内存基线趋于稳定。

### 11.3 案例三：滚动时严重掉帧

问题代码：

```js
window.addEventListener('scroll', () => {
  for (const card of cards) {
    const rect = card.getBoundingClientRect();

    if (rect.top < window.innerHeight) {
      card.style.transform = `translateY(${window.scrollY * 0.1}px)`;
    }
  }
});
```

问题来自三个方面：1）滚动事件触发频繁； 2）每次遍历所有卡片并读取布局； 3）读取和写入发生在同一循环中，可能反复触发布局。

先使用 `requestAnimationFrame` 合并同一帧中的多次事件，并分开读取和写入：

```js
let scheduled = false;
let latestScrollY = 0;

window.addEventListener('scroll', () => {
  latestScrollY = window.scrollY;

  if (scheduled) return;
  scheduled = true;

  requestAnimationFrame(() => {
    const visibleCards = [];

    for (const card of cards) {
      const rect = card.getBoundingClientRect();
      if (rect.top < window.innerHeight && rect.bottom > 0) {
        visibleCards.push(card);
      }
    }

    for (const card of visibleCards) {
      card.style.transform = `translateY(${latestScrollY * 0.1}px)`;
    }

    scheduled = false;
  });
}, { passive: true });
```

这段代码仍然读取所有卡片。元素非常多时，应使用 `IntersectionObserver` 维护可见集合，或直接使用虚拟列表减少 DOM 总量。

Performance 面板应验证：每帧 JavaScript 时间下降、Layout 次数减少、掉帧区间缩短。

### 11.4 案例四：GC 频繁但没有泄漏

动画运行时周期性卡顿，但内存在 GC 后可以回落。Allocation Sampling 显示每帧创建大量点对象：

```js
function transform(points) {
  return points.map((point) => ({
    x: point.x * scale,
    y: point.y * scale
  }));
}
```

这里没有长期保留对象，但分配速率过高，新生代频繁填满并触发 Minor GC。

如果分析证明这是热点，可以复用输出缓冲区：

```js
function transform(points, output) {
  output.length = points.length;

  for (let i = 0; i < points.length; i += 1) {
    const target = output[i] ?? (output[i] = { x: 0, y: 0 });
    target.x = points[i].x * scale;
    target.y = points[i].y * scale;
  }

  return output;
}
```

对象复用引入了可变状态，代码更难维护。只有真实分配分析证明收益明显时才这样优化。

## 12. 高频面试题与回答

### 12.1 V8 是怎样执行 JavaScript 的

> V8 先把源码解析为 AST，再由 Ignition 生成字节码并尽快开始执行。执行过程中引擎收集类型和对象结构反馈，频繁执行的热点代码会交给 TurboFan 优化为更专门的机器码。如果后续输入类型或对象结构破坏了优化假设，引擎会反优化，退回更通用的执行方式。分层执行同时兼顾启动速度和长期运行性能。

### 12.2 Hidden Class 和 Inline Cache 是什么

> JavaScript 对象结构可以动态变化，V8 会用 Hidden Class 描述对象布局。相同顺序创建相同属性的对象更可能共享结构。属性访问第一次完成查找后，Inline Cache 会在该访问位置记录对象结构和属性位置；后续遇到相同结构就能走快速路径。如果一个位置接收大量不同结构，缓存会变得多态甚至超多态，属性访问只能使用更通用的方式。

### 12.3 V8 垃圾回收机制

> V8 以可达性判断对象是否存活，从 GC Root 出发标记所有可达对象。它根据多数对象生命周期很短的规律进行分代：新生代通过 Minor GC 复制少量存活对象，多轮存活的对象晋升到老生代；老生代主要使用标记清除和标记整理。现代 GC 使用增量、并发和并行降低主线程长暂停，并通过写屏障保证引用变化不会造成漏标。

### 12.4 什么是内存泄漏，如何排查

> 内存泄漏是对象业务上已经失效，但仍能从 GC Root 到达。常见原因有无边界全局缓存、闭包持有大对象、定时器和监听器未清理、Observer 未断开以及 Detached DOM。排查时重复执行同一操作、等待 GC、比较多份 Heap Snapshot，再沿 Retainer Chain 找到持有者。修复后用相同场景确认对象数量和内存基线不再持续增长。

### 12.5 为什么 JavaScript 会让页面卡顿

> JavaScript、用户输入、样式和布局等工作共享浏览器主线程。一个 JavaScript 任务开始后不会被普通输入和渲染随意打断，因此长任务会让用户事件和下一帧等待。任务结束后还要清空微任务，持续产生微任务也可能推迟渲染。优化时先减少工作量，再根据场景拆分任务、使用 requestAnimationFrame，或把独立 CPU 计算移到 Worker。

### 12.6 重排和重绘有什么区别

> 布局也叫重排，用来计算元素的尺寸和位置；绘制根据布局结果生成文本、背景、边框等绘制指令；合成把图层组合成最终画面。修改尺寸通常会触发布局并影响后续绘制，修改颜色一般不需要布局，而 transform 和 opacity 更有机会只更新合成。真正优化时应在 Performance 面板确认修改实际触发了哪些阶段。

### 12.7 什么是强制同步布局

> 浏览器通常会批量处理样式修改。如果 JavaScript 写入样式后立即读取 offsetWidth、getBoundingClientRect 等几何信息，为了返回最新值，浏览器必须提前执行样式计算和布局。循环中反复读写会形成 Layout Thrashing。解决方式是集中读取、完成计算后再集中写入。

### 12.8 性能优化的一般流程

> 先把“慢”定义成可测量的用户现象，再用 Performance、Memory 或线上指标定位瓶颈。优化时优先减少无意义工作、数据规模和执行次数，其次改进算法与调度方式，最后才考虑微观代码技巧。修改后必须在相同场景重新测量，确认收益真实、功能正确，并且没有把成本转移到内存或其他阶段。

## 13. 最终知识地图

```text
JavaScript 源码
→ AST、字节码、解释执行
→ 热点代码根据类型反馈优化
→ 输入或对象结构变化可能反优化

代码运行并创建对象
→ 新生代快速分配
→ 短命对象由 Minor GC 回收
→ 长期对象晋升老生代
→ Major GC 标记、清除和整理

无用对象仍然可达
→ GC 无法回收
→ 内存基线持续增长
→ 沿 Retainer Chain 找到未断开的引用

JavaScript 任务时间过长
→ 主线程无法处理输入和渲染
→ 交互延迟、动画掉帧
→ 减少工作、拆分任务或使用 Worker

DOM 布局读写交错
→ 浏览器反复同步布局
→ 单帧超过时间预算
→ 集中读取、集中写入、减少 DOM 总量

定义用户问题
→ 使用工具收集证据
→ 修改真正瓶颈
→ 相同条件重新验证
```
