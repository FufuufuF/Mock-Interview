# JavaScript 模块化专题 — 完整笔记

## 一句话总结

JavaScript 模块化解决的是代码之间如何隔离、如何暴露接口、如何声明依赖以及如何加载依赖的问题。它从全局脚本和命名空间，发展到基于闭包的 IIFE，再分化出服务端的 CommonJS 与浏览器端的 AMD、CMD，经过 UMD 兼容阶段，最终发展为语言原生的 ES Modules（ESM）。

---

## 0. 模块化演进全景图

```text
全局脚本
  ↓
命名空间
  ↓
IIFE 模块模式
  ├── 服务端路线：CommonJS ─────────┐
  └── 浏览器路线：AMD / CMD → UMD ─┤
                                     ↓
                          ES Modules（ESM）
                                     ↓
             Node ESM / 浏览器原生 ESM / 打包工具生态
```

这并不是一条完全线性的替代关系：

- CommonJS、AMD 和 CMD 曾经针对不同运行环境并行发展。
- UMD 不是新的加载机制，而是一种兼容多种环境的包装写法。
- ESM 成为语言标准后，CommonJS 仍然长期存在于 Node.js 生态中。
- 现代项目通常使用 ESM 编写源码，再由浏览器、Node.js 或打包工具加载。

学习这段历史时，始终带着四个问题：

1. 如何避免全局变量污染？
2. 如何区分私有成员和公共接口？
3. 模块如何声明、查找并加载依赖？
4. 模块在什么时候执行，导出的值又如何变化？

---

## 1. 模块化之前：全局脚本

### 1.1 多个 script 文件不等于模块化

早期网页通常把代码拆到不同文件，再按顺序引入：

```html
&lt;script src="jquery.js"&gt;&lt;/script&gt;
&lt;script src="user.js"&gt;&lt;/script&gt;
&lt;script src="app.js"&gt;&lt;/script&gt;
```

虽然代码被拆成了多个文件，但它们仍然共享同一个全局作用域。文件只是物理上的拆分，并没有形成语言层面的模块边界。

```js
// user.js
var name = 'Alice';

// app.js
var name = 'Bob';

console.log(name); // "Bob"
```

### 1.2 全局脚本的主要问题

#### 全局变量污染

每个文件都可能向 `window` 写入变量：

```js
var count = 1;

console.log(window.count); // 1（浏览器普通脚本中）
```

变量越多，发生重名的可能性越高。

#### 依赖关系不明确

`app.js` 使用了 `$`，但仅看源码无法确定 `$` 来自哪个文件：

```js
$('#app').show();
```

开发者必须依赖 HTML 中的脚本顺序理解依赖。

#### 加载顺序不可随意改变

如果 `app.js` 依赖 `jquery.js`，就必须先加载 jQuery：

```html
<!-- 顺序错误时，app.js 中的 $ 不存在 -->
&lt;script src="app.js"&gt;&lt;/script&gt;
&lt;script src="jquery.js"&gt;&lt;/script&gt;
```

#### 无法区分私有成员

所有全局变量都可能被外部读取和修改：

```js
var token = 'secret';

// 任意其他脚本都能修改
token = 'changed';
```

### 1.3 模块真正需要具备什么

一个成熟的模块系统通常需要解决：

- **作用域隔离**：模块内部变量不能随意污染外部。
- **接口控制**：明确哪些成员对外公开，哪些成员保持私有。
- **依赖管理**：明确当前模块依赖谁。
- **加载机制**：知道去哪里找到依赖，以及同步还是异步加载。
- **执行规则**：确定模块是否只执行一次、如何缓存、如何处理循环依赖。

## 2. 第一阶段：命名空间模式

### 2.1 使用对象收拢变量

最简单的改进，是把相关变量和函数挂到同一个对象上：

```js
var userModule = {
  name: 'Alice',
  age: 18,
  getName: function () {
    return this.name;
  }
};

userModule.getName(); // "Alice"
```

原来需要三个全局变量，现在只需要一个全局对象 `userModule`。

### 2.2 命名空间的优点

- 减少全局变量数量。
- 相关功能集中在一个对象下。
- 调用来源更加明确，例如 `userModule.getName()`。
- 可以使用多层命名空间避免库之间重名。

```js
var App = {
  user: {
    getName: function () {}
  },
  order: {
    create: function () {}
  }
};
```

### 2.3 命名空间的局限

命名空间只是把全局变量收拢起来，并没有建立真正的私有作用域：

```js
var userModule = {
  token: 'secret',
  getToken: function () {
    return this.token;
  }
};

userModule.token = 'hacked';
userModule.getToken(); // "hacked"
```

外部仍然能够：

- 查看全部内部状态。
- 修改本应私有的数据。
- 删除或替换模块方法。
- 依赖 HTML 中的脚本加载顺序。

因此，下一步需要解决的是：如何产生私有作用域。

## 3. 第二阶段：IIFE 模块模式

### 3.1 IIFE 是什么

IIFE 是 Immediately Invoked Function Expression，即立即调用函数表达式：

```js
(function () {
  console.log('立即执行');
})();
```

函数会创建独立的函数作用域。函数执行结束后，内部变量无法从外部直接访问。

```js
(function () {
  var privateValue = 1;
})();

console.log(privateValue); // ReferenceError
```

### 3.2 IIFE 如何形成模块

利用函数作用域保存私有成员，再通过返回对象暴露公共接口：

```js
var userModule = (function () {
  var name = 'Alice';
  var token = 'secret';

  function getName() {
    return name;
  }

  function setName(value) {
    name = value;
  }

  return {
    getName: getName,
    setName: setName
  };
})();

userModule.getName(); // "Alice"
userModule.setName('Bob');
userModule.getName(); // "Bob"
console.log(userModule.token); // undefined
```

这里同时使用了三个函数专题知识点：

1. IIFE 执行时创建函数作用域。
2. `name` 和 `token` 是函数内部的局部变量。
3. 返回的方法形成闭包，IIFE 执行结束后仍能访问这些变量。

### 3.3 Revealing Module Pattern

这种“先在内部定义，再统一返回公共接口”的写法叫揭示模块模式：

```js
var counterModule = (function () {
  var count = 0;

  function increment() {
    count += 1;
  }

  function getCount() {
    return count;
  }

  return {
    increment: increment,
    getCount: getCount
  };
})();
```

它明确区分了：

- `count`：私有状态。
- `increment`、`getCount`：内部实现。
- 返回对象中的属性：公共 API。

### 3.4 通过参数注入依赖

IIFE 可以把依赖作为参数传入：

```js
var userModule = (function ($) {
  function showUser() {
    $('#user').show();
  }

  return {
    showUser: showUser
  };
})(jQuery);
```

这样做的优点：

- 在函数内部明确 `$` 来自外部注入。
- 可以给依赖设置局部别名。
- 局部变量访问通常比全局查找更直接。

但它并没有真正解决依赖加载问题：在执行模块之前，仍然必须先通过 `<script>` 加载 jQuery。

### 3.5 IIFE 模块的局限

- 每个模块都要手动挂载到全局变量。
- 依赖仍然依靠 `<script>` 的先后顺序。
- 缺少统一的导入、导出语法。
- 无法自动查找和加载依赖文件。
- 模块数量变多后，HTML 中会出现大量 `<script>`。
- 依赖关系复杂时，人工维护顺序非常困难。

IIFE 解决了“作用域隔离”和“接口控制”，但没有完整解决“依赖声明”和“模块加载”。这推动了正式模块规范的出现。

### 3.6 本阶段面试回答

> JavaScript 最早通过多个 script 标签组织代码，但所有文件共享全局作用域，存在变量污染、依赖不明确和加载顺序问题。命名空间模式通过对象收拢变量，只减少了全局变量数量，没有实现私有成员。随后出现 IIFE 模块模式，它利用函数作用域隔离内部变量，并通过闭包暴露公共接口，但依赖仍需手动通过 script 顺序管理，因此还不是真正完整的模块系统。

## 4. 第三阶段：CommonJS

### 4.1 CommonJS 出现的背景

2009 年前后，服务端 JavaScript 开始发展。Node.js 需要一套模块机制来解决：

- 每个文件拥有独立作用域。
- 一个文件可以主动导出接口。
- 其他文件可以声明并加载依赖。
- 模块能够被定位、执行和缓存。

CommonJS 规范提供了三个核心概念：

```js
require()       // 导入模块
module.exports  // 当前模块最终导出的内容
exports         // module.exports 的初始别名
```

CommonJS 最典型的实现就是 Node.js 的 CommonJS 模块系统。

### 4.2 CommonJS 基本使用

导出模块：

```js
// math.js
function add(a, b) {
  return a + b;
}

function subtract(a, b) {
  return a - b;
}

module.exports = {
  add,
  subtract
};
```

导入模块：

```js
// app.js
const math = require('./math');

math.add(1, 2);      // 3
math.subtract(5, 2); // 3
```

也可以解构：

```js
const { add, subtract } = require('./math');
```

### 4.3 一个文件就是一个模块

在 Node.js CommonJS 中，每个文件都有自己的模块作用域：

```js
// a.js
const value = 1;

// b.js
console.log(value); // ReferenceError
```

`a.js` 的变量不会自动成为全局变量。只有显式放到 `module.exports` 上的内容才会被其他模块获得。

### 4.4 Node 的模块包装函数

Node.js 在执行 CommonJS 文件前，会在概念上把源码包装为一个函数：

```js
(function (exports, require, module, __filename, __dirname) {
  // 模块源代码
});
```

例如：

```js
const value = 1;
module.exports = value;
```

可以理解为：

```js
(function (exports, require, module, __filename, __dirname) {
  const value = 1;
  module.exports = value;
});
```

这解释了几个常见问题：

- 为什么不同文件中的变量不会互相污染：每个文件都在独立函数中执行。
- 为什么模块中可以直接使用 `require`：它是包装函数的参数。
- 为什么可以直接使用 `module` 和 `exports`：它们也是参数。
- 为什么 CommonJS 顶层 `this` 不是浏览器中的 `window`。
- 为什么有 `__filename` 和 `__dirname`。

严格来说，这个包装函数是理解模型；Node 内部实现还包括编译、缓存、扩展处理等步骤。

### 4.5 `module.exports` 与 `exports`

模块初始化时，可以近似理解为：

```js
const module = {
  exports: {}
};

const exports = module.exports;
```

因此，下面的写法有效：

```js
exports.add = function (a, b) {
  return a + b;
};
```

它等价于：

```js
module.exports.add = function (a, b) {
  return a + b;
};
```

因为两者最初指向同一个对象。

#### 为什么不能直接给 exports 重新赋值

```js
// 错误理解：希望导出函数
exports = function add(a, b) {
  return a + b;
};
```

这里仅仅让局部变量 `exports` 指向了新函数，没有修改 `module.exports`：

```js
exports = newValue;
// module.exports 仍然指向原来的 {}
```

Node 最终返回的是 `module.exports`，所以正确写法是：

```js
module.exports = function add(a, b) {
  return a + b;
};
```

记忆方式：

> `exports` 只是初始别名，真正决定模块导出结果的是 `module.exports`。

#### 混合赋值时看最终指向

```js
exports.a = 1;
module.exports = { b: 2 };
exports.c = 3;
```

最终导出：

```js
{ b: 2 }
```

原因是第二行替换了 `module.exports`，此后旧的 `exports` 仍指向原对象，给它添加 `c` 不会影响新的导出对象。

### 4.6 `require` 的加载过程

执行：

```js
const math = require('./math');
```

可以从面试角度概括为五步：

1. **解析标识符**：判断是核心模块、相对路径、绝对路径还是第三方包。
2. **定位文件**：根据路径、扩展名和包配置找到目标模块。
3. **检查缓存**：如果模块已经加载，直接返回缓存中的导出。
4. **创建并执行模块**：创建 `module` 对象，用包装函数执行源码。
5. **缓存并返回**：返回 `module.exports`。

概念伪代码：

```js
function require(id) {
  const filename = resolve(id);

  if (cache[filename]) {
    return cache[filename].exports;
  }

  const module = {
    exports: {},
    loaded: false
  };

  cache[filename] = module;
  executeModule(filename, module);
  module.loaded = true;

  return module.exports;
}
```

注意：模块会在执行完成之前就放入缓存，这一点是 CommonJS 处理循环依赖的关键。

### 4.7 CommonJS 为什么同步加载

```js
const data = require('./data');
console.log(data);
```

`require` 返回后，下一行就可以立即使用模块，因此它是同步接口。

在 Node.js 中，模块通常位于本地磁盘，读取速度相对可控，启动阶段同步加载也更容易编写。

但浏览器模块可能需要经过网络下载。如果每次 `require` 都同步等待网络，会长时间阻塞页面，所以 CommonJS 原生机制不适合直接在浏览器运行。

这正是后来 AMD 等浏览器异步模块方案出现的重要原因。

### 4.8 模块只执行一次与缓存

```js
// counter.js
console.log('counter 执行');

let count = 0;
count += 1;

module.exports = { count };
```

```js
// app.js
const a = require('./counter');
const b = require('./counter');

console.log(a === b); // true
```

通常情况下：

- `counter.js` 只执行一次。
- 第二次 `require` 直接读取缓存。
- `a` 和 `b` 获得同一个导出对象引用。

缓存键通常是模块解析后的绝对文件名，而不是源码中写下的原始字符串。

#### 缓存的意义

- 避免重复读取和执行文件。
- 保证模块初始化只发生一次。
- 允许模块维护跨导入方共享的状态。

```js
// store.js
module.exports = {
  count: 0
};

// a.js 和 b.js require 后操作的是同一个对象
```

### 4.9 CommonJS 导出的是值拷贝还是引用

面试中常听到：

> CommonJS 导出的是值拷贝，ESM 导出的是值的动态绑定。

这句话便于对比，但不够精确。更准确的理解是：

> `require()` 在模块执行后取得当时的 `module.exports`。如果取得的是基本类型，就表现为固定值；如果取得的是对象，则拿到的是该对象的引用。CommonJS 不会像 ESM 一样为每个命名导出建立语言层面的实时绑定。

#### 基本类型的例子

```js
// counter.js
let count = 0;

setInterval(() => {
  count += 1;
}, 1000);

module.exports = count;
```

```js
const count = require('./counter');

setTimeout(() => {
  console.log(count); // 仍然是导出时的 0
}, 3000);
```

`module.exports = count` 把当时的数字赋给了导出值，之后内部变量 `count` 变化不会自动更新它。

#### 对象引用的例子

```js
// counter.js
const state = { count: 0 };

setInterval(() => {
  state.count += 1;
}, 1000);

module.exports = state;
```

```js
const state = require('./counter');

setTimeout(() => {
  console.log(state.count); // 可以看到变化
}, 3000);
```

因为导入方持有的是同一个对象引用。

#### 解构可能产生快照

```js
// store.js
module.exports = { count: 0 };
```

```js
const store = require('./store');
const { count } = require('./store');

store.count = 10;

console.log(store.count); // 10
console.log(count);       // 0
```

这里的 `count` 是普通 JavaScript 解构得到的变量，不会随着对象属性实时更新。

### 4.10 CommonJS 的动态性

`require` 本质上是运行时函数调用，因此可以写在条件、循环或函数内部：

```js
if (process.env.NODE_ENV === 'development') {
  const debug = require('./debug');
  debug.start();
}
```

也可以动态计算路径：

```js
const moduleName = './modules/' + name;
const moduleValue = require(moduleName);
```

这种动态性非常灵活，但也使工具难以仅靠静态分析就确定全部依赖，因此传统 CommonJS 不利于 Tree Shaking。

### 4.11 CommonJS 循环依赖

假设 `a.js` 依赖 `b.js`，同时 `b.js` 又依赖 `a.js`：

```js
// a.js
console.log('a 开始');
exports.done = false;

const b = require('./b');
console.log('a 中的 b.done：', b.done);

exports.done = true;
console.log('a 结束');
```

```js
// b.js
console.log('b 开始');
exports.done = false;

const a = require('./a');
console.log('b 中的 a.done：', a.done);

exports.done = true;
console.log('b 结束');
```

```js
// main.js
const a = require('./a');
const b = require('./b');

console.log(a.done, b.done);
```

执行大致如下：

1. `main` 开始加载 `a`。
2. `a` 被提前放进缓存，随后设置 `exports.done = false`。
3. `a` 开始加载 `b`。
4. `b` 被提前放进缓存，随后设置 `exports.done = false`。
5. `b` 再加载 `a`，发现缓存中已有 `a`。
6. 此时 `a` 尚未执行完成，`b` 得到的是 `a` 当前的部分导出 `{ done: false }`。
7. `b` 执行完成。
8. `a` 继续执行并完成。

CommonJS 处理循环依赖的核心是：

> 返回已经执行到当前位置的部分导出，而不是等待整个依赖链全部执行完。

因此循环依赖可能导致：

- 获得尚未初始化完整的对象。
- 某些属性还是 `undefined`。
- 代码行为与模块加载顺序相关。

最好的处理方式通常不是依赖其容错规则，而是重构依赖关系，例如提取公共模块或进行依赖注入。

### 4.12 CommonJS 的优缺点

优点：

- 语法简单，使用方便。
- 每个文件拥有模块作用域。
- 适合 Node.js 本地文件的同步加载。
- 模块有缓存，只执行一次。
- `require` 可以动态调用。
- Node.js 生态长期积累了大量 CommonJS 包。

缺点：

- 同步加载不适合浏览器网络环境。
- 依赖关系可以在运行时变化，不利于静态分析。
- 难以进行可靠的 Tree Shaking。
- 循环依赖时可能得到未完成的部分导出。
- 与 ESM 混用时存在互操作规则和工具差异。

### 4.13 CommonJS 面试回答模板

> CommonJS 主要用于 Node.js。一个文件就是一个模块，Node 会用函数包装文件，从而形成模块作用域，并注入 exports、require、module、__filename 和 __dirname。模块通过 require 同步加载，通过 module.exports 导出；exports 只是 module.exports 的初始别名。模块第一次加载时会执行并进入缓存，之后重复 require 通常直接返回缓存。循环依赖时，CommonJS 返回已经执行部分的 exports。它的动态和同步特性适合服务端，但不利于浏览器网络加载、静态分析和 Tree Shaking。

## 5. 浏览器路线：AMD

### 5.1 为什么浏览器需要另一套方案

CommonJS 使用同步 `require`：

```js
const moduleValue = require('./module');
use(moduleValue);
```

在服务端，模块通常来自本地磁盘；在浏览器中，模块往往需要通过网络获取。如果同步等待网络响应，页面主线程就会被阻塞。

浏览器模块系统需要解决：

- 异步下载模块。
- 下载完成后再执行依赖模块。
- 管理多个模块之间的依赖顺序。
- 避免手工维护大量 `<script>` 标签。

AMD 因此出现。

### 5.2 AMD 是什么

AMD 是 Asynchronous Module Definition，即异步模块定义。它主张：

- 使用 `define` 定义模块。
- 在依赖数组中提前声明依赖。
- 等依赖异步加载完成后，执行模块工厂函数。

RequireJS 是 AMD 最知名的实现。

### 5.3 AMD 基本语法

定义无依赖模块：

```js
define(function () {
  function add(a, b) {
    return a + b;
  }

  return {
    add: add
  };
});
```

定义有依赖模块：

```js
define(['jquery', './user'], function ($, user) {
  function render() {
    $('#app').text(user.name);
  }

  return {
    render: render
  };
});
```

使用模块：

```js
require(['./app'], function (app) {
  app.render();
});
```

依赖数组与工厂函数参数按位置对应：

```js
define(['a', 'b'], function (a, b) {
  // 第一个依赖对应参数 a，第二个依赖对应参数 b
});
```

### 5.4 AMD 的“依赖前置”

AMD 通常在定义模块时就把依赖写在数组中：

```js
define(['a', 'b', 'c'], function (a, b, c) {
  // 模块逻辑
});
```

模块工厂执行前，加载器会先处理 `a`、`b`、`c`。这种形式称为依赖前置。

优点：加载器可以较早知道依赖关系，并行发起网络请求。

局限：即使某个依赖只在条件分支中使用，传统写法也会提前声明和加载，代码阅读时依赖与使用位置相距较远。

### 5.5 AMD 的优缺点

优点：

- 适合浏览器异步加载环境。
- 可以并行下载多个依赖。
- 明确声明依赖关系。
- 减少手动维护 `<script>` 顺序的负担。

缺点：

- 语法嵌套较多，模块复杂时可读性下降。
- 依赖数组与函数参数必须保持顺序一致。
- 与 CommonJS 写法差异较大。
- 今天已经很少在新项目中直接使用。

## 6. 浏览器路线：CMD

### 6.1 CMD 是什么

CMD 是 Common Module Definition。SeaJS 是其代表实现。

CMD 同样面向浏览器异步加载，但 API 风格更接近 CommonJS，强调依赖就近书写：

```js
define(function (require, exports, module) {
  const a = require('./a');
  a.run();

  exports.start = function () {
    const b = require('./b');
    b.run();
  };
});
```

### 6.2 依赖就近

AMD 常见写法：

```js
define(['./a', './b'], function (a, b) {
  a.run();

  if (condition) {
    b.run();
  }
});
```

CMD 常见写法：

```js
define(function (require) {
  const a = require('./a');
  a.run();

  if (condition) {
    const b = require('./b');
    b.run();
  }
});
```

CMD 把依赖声明放在使用位置附近，因此称为依赖就近。

### 6.3 AMD 与 CMD 的经典对比

面试资料中通常这样概括：

| 维度 | AMD | CMD |
|------|-----|-----|
| 代表实现 | RequireJS | SeaJS |
| 主要环境 | 浏览器 | 浏览器 |
| 依赖书写 | 依赖前置 | 依赖就近 |
| 风格 | 提前列出依赖数组 | 接近 CommonJS 的 `require` |
| 加载思想 | 尽早加载依赖 | 在使用处声明依赖 |

需要注意：不同加载器版本的预加载、延迟执行细节并不能只靠一句“AMD 提前执行，CMD 延迟执行”完全说明。面试时抓住二者最稳定的区别即可：

> AMD 使用依赖数组前置声明；CMD 的 API 风格更接近 CommonJS，强调在使用位置附近 `require`。

### 6.4 AMD、CMD 为什么逐渐退出主流

- ESM 已经成为 JavaScript 语言标准。
- 现代浏览器原生支持 ESM。
- Webpack、Rollup、Vite 等工具可以处理模块依赖。
- ESM 语法更统一，也更适合静态分析。

AMD 和 CMD 今天主要作为模块化演进史和旧项目维护知识出现。

## 7. 兼容阶段：UMD

### 7.1 UMD 为什么出现

同一个库可能需要运行在不同环境：

- Node.js 使用 CommonJS。
- 浏览器项目可能使用 AMD。
- 没有模块加载器的网页只能使用全局变量。

库作者如果分别维护多个版本，成本很高。UMD 因此出现。

UMD 是 Universal Module Definition，即通用模块定义。它不是独立的模块加载规范，而是一种环境检测与包装模板。

### 7.2 UMD 的基本结构

简化版本：

```js
(function (root, factory) {
  if (typeof define === 'function' && define.amd) {
    // AMD 环境
    define(['dependency'], factory);
  } else if (typeof module === 'object' && module.exports) {
    // CommonJS 环境
    module.exports = factory(require('dependency'));
  } else {
    // 普通浏览器全局环境
    root.myLibrary = factory(root.dependency);
  }
})(typeof globalThis !== 'undefined' ? globalThis : this, function (dependency) {
  function run() {
    return dependency.doSomething();
  }

  return {
    run: run
  };
});
```

它的核心流程是：

1. 检测是否存在 AMD 加载器。
2. 否则检测是否处于 CommonJS 环境。
3. 如果都不是，就把库挂载到全局对象。
4. 三种环境最终共用同一个工厂函数。

### 7.3 UMD 的价值

- 一个构建产物可以兼容多种旧模块环境。
- 方便库通过 `<script>` 直接使用。
- 适合模块规范尚未统一的历史阶段。

很多早期前端库会同时发布：

- CommonJS 构建。
- AMD/UMD 构建。
- 浏览器压缩版全局构建。

### 7.4 UMD 的局限

- 包装代码复杂，可读性较低。
- 靠运行时检测环境，不具备 ESM 的静态结构。
- 不利于原生 Tree Shaking。
- 随着 ESM 普及，新项目通常直接发布 ESM 或 ESM + CommonJS 双版本。

### 7.5 浏览器路线面试回答模板

> CommonJS 的同步 require 适合 Node 本地文件，但不适合浏览器网络加载，因此浏览器端出现了 AMD 和 CMD。AMD 以 RequireJS 为代表，通过依赖数组前置声明并异步加载依赖；CMD 以 SeaJS 为代表，API 更接近 CommonJS，强调依赖就近。为了让同一个库同时兼容 AMD、CommonJS 和普通 script 全局变量，又出现了 UMD。UMD 本质是环境检测包装，并不是新的加载器。后来 ESM 成为语言标准，这些方案逐渐退出新项目。

## 8. 语言标准：ES Modules

### 8.1 ESM 出现的意义

ES Modules，简称 ESM，是 ECMAScript 2015（ES6）加入语言标准的模块系统。

在 ESM 之前，CommonJS、AMD、CMD 都是社区规范或运行环境提供的机制；JavaScript 语言本身并不知道什么是模块。ESM 第一次在语法层面规定了：

- 如何导入依赖。
- 如何导出接口。
- 模块作用域如何工作。
- 模块如何链接和执行。
- 导入导出之间如何保持绑定关系。

核心语法是：

```js
import ... from '...';
export ...;
```

### 8.2 命名导出

可以在声明时导出：

```js
// math.js
export const PI = 3.14159;

export function add(a, b) {
  return a + b;
}

export class Calculator {}
```

导入时必须使用对应名称：

```js
import { PI, add, Calculator } from './math.js';
```

也可以先声明，再统一导出：

```js
const PI = 3.14159;

function add(a, b) {
  return a + b;
}

export { PI, add };
```

### 8.3 导入与导出重命名

导出时重命名：

```js
const internalName = 'Alice';

export {
  internalName as userName
};
```

导入时重命名：

```js
import { userName as name } from './user.js';

console.log(name);
```

重命名可以解决不同模块导出同名成员的问题：

```js
import { format as formatDate } from './date.js';
import { format as formatPrice } from './price.js';
```

### 8.4 默认导出

一个模块最多只能有一个默认导出：

```js
// user.js
export default function getUser() {
  return { name: 'Alice' };
}
```

导入默认导出时，名称由导入方决定：

```js
import getUser from './user.js';
```

可以换成其他名称：

```js
import loadUser from './user.js';
```

默认导出表达式：

```js
const config = {
  baseURL: '/api'
};

export default config;
```

也可以直接导出表达式：

```js
export default {
  baseURL: '/api'
};
```

### 8.5 默认导出与命名导出可以共存

```js
// user.js
export const role = 'admin';

export function validate() {
  return true;
}

export default class User {}
```

```js
import User, { role, validate } from './user.js';
```

语法上：

- 花括号外的是默认导入。
- 花括号内的是命名导入。

### 8.6 `export default` 容易混淆的细节

下面是声明一个有名字的函数并默认导出：

```js
export default function foo() {}
```

下面是把变量当前的值作为默认导出表达式：

```js
let value = 1;
export default value;
```

后续修改：

```js
value = 2;
```

导入方通常不会因为这个赋值而获得新的默认值，因为默认导出绑定的是导出表达式当时产生的值。

如果希望导出一个可变化的实时绑定，可以使用命名导出：

```js
export let value = 1;

export function update() {
  value = 2;
}
```

### 8.7 整体导入

可以把模块的全部命名导出收集成模块命名空间对象：

```js
import * as math from './math.js';

math.add(1, 2);
console.log(math.PI);
```

`math` 是模块命名空间对象。它反映模块的导出绑定，但不能像普通对象一样随意覆盖导入成员：

```js
math.PI = 3; // TypeError 或赋值失败
```

### 8.8 只执行模块，不接收导出

有时导入模块只是为了执行其副作用：

```js
import './polyfill.js';
import './global-style.css'; // 是否支持由构建工具决定
```

第一种 JavaScript 导入称为副作用导入。模块会被加载并执行，但当前文件不绑定任何导出成员。

常见场景：

- 注册全局能力。
- 加载 polyfill。
- 执行初始化逻辑。
- 在构建工具环境中导入全局样式。

### 8.9 重新导出

从另一个模块导入后再导出：

```js
import { add } from './math.js';
export { add };
```

可以缩写为：

```js
export { add } from './math.js';
```

重新导出时重命名：

```js
export { add as sum } from './math.js';
```

批量重新导出：

```js
export * from './math.js';
```

需要注意：`export *` 默认不会转发另一个模块的 `default` 导出。

显式转发默认导出：

```js
export { default } from './user.js';
```

或转换成命名导出：

```js
export { default as User } from './user.js';
```

### 8.10 Barrel File 聚合模块

通过 `index.js` 统一聚合多个模块：

```js
// components/index.js
export { default as Button } from './Button.js';
export { default as Modal } from './Modal.js';
export { formatDate } from './utils.js';
```

使用方：

```js
import { Button, Modal, formatDate } from './components/index.js';
```

优点：

- 简化导入路径。
- 对外形成统一入口。
- 隐藏内部目录结构。

风险：

- 大量聚合可能更容易形成循环依赖。
- 某些工具配置下会影响增量构建或 Tree Shaking 效果。
- 公共入口可能让模块边界变得模糊。

### 8.11 ESM 是静态结构

静态 `import` 和 `export` 通常只能出现在模块顶层：

```js
// SyntaxError
if (condition) {
  import { add } from './math.js';
}
```

也不能像普通函数一样动态拼接静态导入路径：

```js
// SyntaxError
const path = './' + name + '.js';
import value from path;
```

这样设计使引擎和构建工具在执行代码之前，就能分析模块依赖图：

- 当前模块依赖哪些模块。
- 当前模块导出了哪些成员。
- 导入成员来自哪个模块。
- 哪些导出可能没有被使用。

这为静态检查、Tree Shaking、预加载和优化提供了基础。

需要条件加载时，使用后面会讲到的 `import()`。

### 8.12 导入声明会提升吗

静态导入在模块执行前就已经完成链接，不能把它简单理解为“代码运行到 import 这一行才加载”：

```js
console.log(value);

import { value } from './module.js';
```

只要 `value` 已经在依赖模块中完成初始化，这种写法可以访问它。不过为了可读性，通常仍把 `import` 写在文件顶部。

更准确的表达是：

> `import` 声明具有静态、顶层的链接语义，模块依赖会在当前模块代码执行前被实例化和求值，而不是像普通函数调用一样按行执行。

### 8.13 ESM 的模块作用域

ESM 顶层声明不会自动挂到全局对象：

```js
// module.js
const value = 1;

console.log(globalThis.value); // undefined
```

不同模块可以安全声明同名变量：

```js
// a.js
const name = 'A';

// b.js
const name = 'B';
```

### 8.14 ESM 自动使用严格模式

ESM 无需手动写 `'use strict'`，默认就是严格模式：

```js
// module.js
undeclared = 1; // ReferenceError
```

其他严格模式行为同样生效，例如普通函数调用中的 `this` 是 `undefined`。

### 8.15 ESM 顶层 this

ESM 顶层 `this` 是 `undefined`：

```js
console.log(this); // undefined
```

普通浏览器经典脚本的顶层 `this` 通常是 `window`。这是面试常见对比点。

如果需要跨环境访问全局对象，应使用：

```js
globalThis
```

### 8.16 导入成员是只读绑定

```js
// counter.js
export let count = 0;

export function increment() {
  count += 1;
}
```

```js
// app.js
import { count, increment } from './counter.js';

increment();
console.log(count); // 1

count = 10; // TypeError：不能由导入方重新赋值
```

“只读”指的是导入绑定本身不能被重新赋值。如果导出的是对象，导入方仍可能修改对象内部属性：

```js
// store.js
export const store = { count: 0 };
```

```js
import { store } from './store.js';

store = {};          // 不允许
store.count = 1;     // 语法层面允许修改对象属性
```

ESM 并不会自动让对象变成不可变对象。

### 8.17 浏览器原生使用 ESM

HTML 中通过 `type="module"` 声明模块脚本：

```html
&lt;script type="module" src="./main.js"&gt;&lt;/script&gt;
```

`main.js`：

```js
import { add } from './math.js';

console.log(add(1, 2));
```

浏览器会解析 `main.js` 的依赖，再请求相应模块。

### 8.18 `type="module"` 的重要特征

#### 默认延迟执行

模块脚本默认行为类似 `defer`：

- HTML 解析与模块下载可以并行。
- 模块会等待依赖下载并解析。
- 通常在 HTML 解析完成后执行。
- 多个模块脚本一般按文档顺序执行，但顶层 `await` 等因素可能影响依赖图的求值时机。

因此通常不需要再写：

```html
&lt;script type="module" defer src="./main.js"&gt;&lt;/script&gt;
```

`defer` 对模块脚本没有额外意义。

#### 同一模块通常只执行一次

浏览器会维护模块映射，同一个规范化 URL 对应的模块通常只实例化并执行一次：

```js
import './init.js';
import './init.js';
```

`init.js` 不会因为重复导入而重复执行。

#### 遵循 CORS

跨域模块请求必须满足 CORS。模块脚本不会像某些传统 `<script>` 那样绕过同源读取限制。

服务器需要返回正确的访问控制响应头。

#### MIME Type 必须正确

模块响应通常需要正确的 JavaScript MIME 类型。如果服务器把 `.js` 返回为 `text/html`，浏览器可能拒绝执行。

常见原因是路径错误后服务器返回了 HTML 404 页面。

#### 相对路径通常需要完整扩展名

浏览器不会像某些 CommonJS 解析器那样自动尝试 `.js`：

```js
// 浏览器原生 ESM 推荐
import { add } from './math.js';
```

下面的路径是否工作取决于服务器和工具，原生浏览器不会自动补全：

```js
import { add } from './math';
```

### 8.19 经典脚本、defer、async 与 module

| 写法 | 下载 | 执行时机 | 顺序 | 作用域/模式 |
|------|------|----------|------|-------------|
| 普通 `<script>` | 遇到标签时下载 | 通常阻塞 HTML 解析并立即执行 | 文档顺序 | 经典脚本规则 |
| `<script defer>` | 并行下载 | HTML 解析完成后、DOMContentLoaded 前 | 保持文档顺序 | 经典脚本规则 |
| `<script async>` | 并行下载 | 下载完成后尽快执行 | 不保证顺序 | 经典脚本规则 |
| `<script type="module">` | 并行下载模块图 | 默认延迟执行 | 按模块依赖求值 | 模块作用域、严格模式 |

如果给模块脚本加 `async`：

```html
&lt;script type="module" async src="./main.js"&gt;&lt;/script&gt;
```

它会在模块及依赖准备好后尽快执行，不再等待文档解析完成或其他模块脚本的默认顺序。适用于与页面其他脚本没有顺序依赖的入口。

### 8.20 裸模块说明符与 Import Maps

浏览器原生 ESM 可以直接理解相对 URL：

```js
import { add } from './math.js';
```

但它默认不知道下面的 `lodash-es` 应该映射到哪个 URL：

```js
import debounce from 'lodash-es/debounce.js';
```

这种不以 `/`、`./` 或 `../` 开头的写法称为裸模块说明符。打包工具和 Node.js 有自己的包解析规则，浏览器原生环境可以使用 Import Maps 建立映射：

```html
&lt;script type="importmap"&gt;
{
  "imports": {
    "lodash-es/": "https://cdn.example.com/lodash-es/"
  }
}
&lt;/script&gt;

&lt;script type="module"&gt;
  import debounce from 'lodash-es/debounce.js';
&lt;/script&gt;
```

Import Maps 的作用类似给模块说明符建立 URL 映射，但它不是 npm 包管理器，也不会自动下载或安装依赖。

### 8.21 ESM 的加载、链接与执行

理解 ESM 不能只停留在“先加载依赖再执行”。面试中可以把它概括为三个主要阶段：

```text
构建（Construction）
  ↓
实例化 / 链接（Instantiation / Linking）
  ↓
求值（Evaluation）
```

不同资料对阶段命名略有差异，但核心过程一致。

#### 第一阶段：构建模块图

从入口模块开始：

1. 获取入口模块源码。
2. 解析源码，找到静态 `import`。
3. 根据模块说明符定位依赖。
4. 递归获取并解析依赖。
5. 最终形成模块依赖图。

```text
main.js
├── user.js
│   └── request.js
└── config.js
```

解析阶段主要确定结构，并不等于已经执行了所有模块代码。

#### 第二阶段：实例化与链接

引擎为模块创建模块记录和环境，建立导入与导出之间的绑定关系：

```js
// counter.js
export let count = 0;
```

```js
// app.js
import { count } from './counter.js';
```

`app.js` 中的导入绑定会连接到 `counter.js` 中的导出绑定。它不是简单复制一个普通变量值。

这个阶段还会检查：

- 导入名称是否真的被目标模块导出。
- 重复或冲突的间接导出。
- 整个依赖图中各模块的链接关系。

#### 第三阶段：求值

引擎按照依赖关系执行模块顶层代码，初始化变量并产生副作用。

```js
// dependency.js
console.log('dependency');

// main.js
import './dependency.js';
console.log('main');
```

输出：

```text
dependency
main
```

依赖模块通常先求值，然后入口模块再求值。每个模块在同一模块图中通常只求值一次。

### 8.22 ESM 的 Live Binding

ESM 的命名导出与导入之间是实时绑定，也称 live binding：

```js
// counter.js
export let count = 0;

export function increment() {
  count += 1;
}
```

```js
// app.js
import { count, increment } from './counter.js';

console.log(count); // 0
increment();
console.log(count); // 1
```

导入方读取 `count` 时，会观察到导出模块中该绑定的最新值。

这不是因为 ESM 不断复制新值，而是因为导入和导出被链接到同一个绑定关系。

#### 导出方可以修改，导入方不能重新赋值

```js
// counter.js 内部
count += 1; // 允许
```

```js
// app.js
count += 1; // 不允许
```

导入方只有读取权，导出方保留对自身变量的写入权。

### 8.23 CommonJS 与 ESM 导出行为对比

CommonJS：

```js
// cjs-counter.cjs
let count = 0;

function increment() {
  count += 1;
}

module.exports = {
  count,
  increment
};
```

```js
const counter = require('./cjs-counter.cjs');

counter.increment();
console.log(counter.count); // 仍可能是 0
```

导出对象创建时，属性 `count` 获得了当时的数字 `0`。内部变量改变不会自动改写这个属性。

如果改用 getter，可以人为模拟动态读取：

```js
module.exports = {
  get count() {
    return count;
  },
  increment
};
```

ESM 则由语言层面的绑定机制直接保证命名导出的实时性。

### 8.24 动态导入 `import()`

静态 `import` 不能写在条件语句中，但 `import()` 是运行时表达式：

```js
if (condition) {
  import('./feature.js');
}
```

`import()` 返回 Promise：

```js
import('./math.js')
  .then((module) => {
    console.log(module.add(1, 2));
  })
  .catch((error) => {
    console.error('模块加载失败', error);
  });
```

搭配 `async/await`：

```js
async function loadMath() {
  const module = await import('./math.js');
  return module.add(1, 2);
}
```

返回的是模块命名空间对象：

```js
const module = await import('./user.js');

module.default; // 默认导出
module.role;    // 命名导出
```

#### 动态导入的典型场景

- 路由懒加载。
- 点击后才加载大型组件。
- 根据语言加载国际化文件。
- 按环境或能力加载不同实现。
- 将代码拆分成单独 chunk。

```js
button.addEventListener('click', async () => {
  const { openEditor } = await import('./heavy-editor.js');
  openEditor();
});
```

#### 静态 import 与动态 import 对比

| 维度 | 静态 `import` | 动态 `import()` |
|------|---------------|------------------|
| 形式 | 声明 | 表达式，返回 Promise |
| 位置 | 模块顶层 | 条件、函数等运行时位置 |
| 分析时机 | 执行前静态分析 | 运行时触发 |
| 典型用途 | 核心依赖 | 懒加载、按需加载 |
| 打包结果 | 通常进入静态依赖图 | 通常形成异步 chunk |

### 8.25 `import()` 是否每次都重新执行模块

通常不会。同一个模块成功加载并求值后，重复动态导入会复用模块记录：

```js
const a = await import('./module.js');
const b = await import('./module.js');

console.log(a === b); // 通常为 true
```

模块顶层代码通常只执行一次。`import()` 的异步性不意味着每次都创建一个全新的模块实例。

需要注意，查询参数不同的 URL 可能被视为不同模块：

```js
import './config.js?version=1';
import './config.js?version=2';
```

是否视为相同模块取决于运行环境对模块标识符和 URL 的规范化结果。

### 8.26 顶层 await

在支持的 ESM 环境中，可以直接在模块顶层使用 `await`：

```js
// config.js
const response = await fetch('/config.json');
export const config = await response.json();
```

依赖它的模块会等待其异步求值完成：

```js
// app.js
import { config } from './config.js';

console.log(config);
```

顶层 `await` 只能用于模块，不能直接用于普通经典脚本。

#### 顶层 await 的风险

- 会阻塞依赖当前模块的模块求值。
- 可能把异步等待沿依赖图向上传播。
- 循环依赖叠加异步求值时更难推理。
- 关键初始化失败可能导致整个模块图无法完成求值。

通常应谨慎使用，尤其不要在基础工具模块中随意进行耗时网络请求。

### 8.27 `import.meta`

ESM 没有统一的 CommonJS `__filename` 和 `__dirname`，而是提供 `import.meta`：

```js
console.log(import.meta.url);
```

在浏览器中，它通常是当前模块的完整 URL。可以相对当前模块构造资源 URL：

```js
const imageURL = new URL('./logo.png', import.meta.url);
```

在 Node.js 中，也可以基于它转换文件路径。现代 Node 版本还可能提供更多 `import.meta` 属性，但兼容性应以目标版本为准。

构建工具可能扩展自己的元信息，例如 Vite 的：

```js
import.meta.env
```

这不是 ECMAScript 对所有环境都规定的通用环境变量 API，而是工具提供的能力。

### 8.28 ESM 循环依赖

假设 `a.js` 和 `b.js` 互相导入：

```js
// a.js
import { b } from './b.js';

export const a = 'A';

export function printB() {
  console.log(b);
}
```

```js
// b.js
import { a } from './a.js';

export const b = 'B';

export function printA() {
  console.log(a);
}
```

ESM 可以在实例化阶段先建立绑定关系，即使模块尚未执行完成，也能构建出循环模块图。只要真正读取变量时，它已经初始化，就可能正常工作。

```js
// main.js
import { printB } from './a.js';
import { printA } from './b.js';

printA(); // A
printB(); // B
```

#### 暂时性死区风险

下面的循环依赖可能报错：

```js
// a.js
import { b } from './b.js';
console.log(b);
export const a = 'A';
```

```js
// b.js
import { a } from './a.js';
console.log(a);
export const b = 'B';
```

如果某个模块在另一个模块完成变量初始化前就读取对应绑定，可能触发：

```text
ReferenceError: Cannot access 'a' before initialization
```

原因不是 ESM 没有建立绑定，而是绑定已经存在，但 `let`、`const` 或 `class` 对应的值仍处于暂时性死区。

#### 函数声明有时能缓解问题

```js
// a.js
import { callB } from './b.js';

export function callA() {
  return 'A';
}

export function start() {
  return callB();
}
```

函数声明在模块实例化过程中会较早完成初始化，因此某些循环依赖写法可以工作。但这不代表循环依赖是好的设计。

#### 如何重构循环依赖

- 把双方共同依赖的内容提取到第三个模块。
- 让上层模块负责组合，底层模块不反向依赖上层。
- 通过函数参数或依赖注入传入能力。
- 延迟到函数调用时读取依赖，避免顶层立即访问。
- 减少大型 `index.js` 聚合文件造成的间接环。

```text
重构前：A ↔ B

重构后：
    shared
    ↑   ↑
    A   B
```

### 8.29 CommonJS 与 ESM 循环依赖区别

| 维度 | CommonJS | ESM |
|------|----------|-----|
| 建立关系 | 执行时 `require` | 实例化阶段静态链接 |
| 循环中拿到什么 | 当前已执行部分的 `module.exports` | 指向导出变量的绑定 |
| 常见风险 | 属性尚未添加，得到 `undefined` 或部分对象 | 变量尚未初始化，触发 TDZ 错误 |
| 结果是否易受执行顺序影响 | 是 | 是，尤其顶层立即读取时 |

二者都允许出现循环依赖，但“能够处理”不等于“应该依赖循环结构”。

### 8.30 ESM 错误发生在什么时候

可以把错误粗略分为：

#### 解析错误

源码语法本身不合法：

```js
if (true) {
  import { value } from './a.js';
}
```

#### 链接错误

导入了目标模块不存在的命名导出：

```js
import { missing } from './module.js';
```

如果 `module.js` 没有导出 `missing`，模块链接失败，主体代码不会正常执行。

#### 求值错误

模块顶层代码执行时抛错：

```js
throw new Error('初始化失败');
```

理解这三个阶段有助于解释：为什么某些错误在业务逻辑运行前就发生，以及为什么整个依赖链可能因此无法求值。

### 8.31 ESM 面试回答模板

> ESM 是 ES6 加入语言标准的原生模块系统，使用 import 和 export。它具有静态结构，引擎能在执行前构建模块图，并经过解析、实例化链接和求值阶段。命名导入不是普通值拷贝，而是指向导出变量的只读实时绑定：导出方更新后，导入方能读到最新值，但不能直接重新赋值。静态结构使 Tree Shaking 等优化成为可能。需要运行时按需加载时使用返回 Promise 的 import()。ESM 循环依赖会先建立绑定，但如果在变量初始化前读取，仍可能触发暂时性死区错误。

## 9. CommonJS 与 ESM 总对比

### 9.1 核心对比表

| 维度 | CommonJS | ESM |
|------|----------|-----|
| 产生背景 | 社区规范，Node.js 广泛实现 | ECMAScript 语言标准 |
| 核心语法 | `require`、`module.exports` | `import`、`export` |
| 依赖分析 | 运行时、动态 | 静态 `import` 可在执行前分析 |
| 加载接口 | `require` 是同步调用 | 静态加载与链接；`import()` 异步 |
| 导出模型 | 返回 `module.exports` 的当前结果 | 导入与导出建立 live binding |
| 导入方写入 | 对取得的普通对象按 JS 规则操作 | 不能重新赋值导入绑定 |
| 条件加载 | 可在条件中 `require` | 静态 import 不可；可用 `import()` |
| 顶层 this | Node CJS 中通常是 `module.exports` | `undefined` |
| 严格模式 | 不自动开启 | 自动严格模式 |
| Tree Shaking | 较困难 | 静态结构天然更适合 |
| 循环依赖 | 返回部分执行的 exports | 先建绑定，提前读取可能触发 TDZ |
| 浏览器原生支持 | 不支持，需要工具 | 现代浏览器支持 |
| Node.js 支持 | 长期原生支持 | 现代 Node 原生支持 |

### 9.2 “运行时加载”和“编译时加载”怎么说才准确

常见回答是：

> CommonJS 是运行时加载，ESM 是编译时加载。

这句话想表达的是：

- CommonJS 的 `require()` 是普通运行时函数调用，依赖可以动态决定。
- ESM 的静态 `import` 语法可以在模块执行前被解析并建立链接。

但“ESM 在编译时已经把网络文件全部加载完成”并不准确。浏览器仍然需要在运行时请求模块资源。

更严谨的回答：

> CommonJS 的依赖关系主要在代码执行时由 require 确定；ESM 的静态导入导出结构能在模块执行前被解析、链接，因此工具可以提前构建依赖图。

### 9.3 “值拷贝”和“引用”怎么说才准确

常见简化：

> CommonJS 导出值拷贝，ESM 导出值引用。

更准确的说法：

- CommonJS 返回 `module.exports` 当时指向的值；基本类型表现为固定值，对象仍然按 JavaScript 引用语义共享。
- ESM 命名导入与导出变量建立语言层面的实时绑定，不是普通对象引用，也不是反复进行值拷贝。

不要把 ESM live binding 说成“导入方拿到了变量的内存地址”。规范层面应称为绑定关系。

### 9.4 为什么 ESM 更适合 Tree Shaking

CommonJS 依赖可以动态变化：

```js
const moduleValue = require(condition ? './a' : './b');
```

导出对象也能在运行时修改：

```js
module.exports[key] = value;
```

工具很难仅靠静态分析精确知道最终依赖和导出。

ESM 的静态语法：

```js
import { add } from './math.js';
export { add };
```

使工具可以提前分析哪些导出被使用，再结合副作用分析移除无用代码。

### 9.5 同名语法的常见错误

#### 错把 CommonJS 当成 ESM 默认导出

```js
// CommonJS
module.exports = function fn() {};
```

它并不是语法意义上的 `export default`，只是整个导出值恰好是函数。不同工具在互操作时可能把它映射成默认导入，但这种映射来自运行环境或编译工具。

#### 错把 exports 当作最终导出变量

```js
exports = {};
```

不会替换 `module.exports`。

#### 错把命名导入当成对象解构

```js
import { value } from './module.js';
```

看起来像解构，但它不是普通对象解构：

- 名称在链接阶段校验。
- 它是只读实时绑定。
- 不能写成任意运行时表达式。

### 9.6 面试中的 30 秒回答

> CommonJS 是 Node 生态长期使用的模块系统，通过 require 和 module.exports 在运行时同步加载，依赖可以动态决定，模块结果会缓存。ESM 是语言原生标准，通过静态 import/export 在执行前建立模块图和 live binding，默认严格模式，也更利于 Tree Shaking。CommonJS 循环依赖拿到部分 exports；ESM 循环依赖先建立绑定，但提前读取未初始化变量可能触发 TDZ。在现代项目中优先使用 ESM，维护旧 Node 包时仍会遇到 CommonJS。

## 10. Node.js 中的两套模块系统

### 10.1 Node 如何判断模块类型

Node.js 同时支持 CommonJS 和 ESM。常见判断依据是文件扩展名与最近的 `package.json` 中的 `type` 字段。

#### `.cjs`

明确按 CommonJS 处理：

```js
// math.cjs
module.exports = { add };
```

#### `.mjs`

明确按 ESM 处理：

```js
// math.mjs
export function add() {}
```

#### `.js`

通常由最近的 `package.json` 决定：

```json
{
  "type": "module"
}
```

此时包作用域中的 `.js` 按 ESM 处理。

```json
{
  "type": "commonjs"
}
```

或没有声明 `type` 时，传统 Node 项目中的 `.js` 通常按 CommonJS 处理。

| 文件/配置 | 解释方式 |
|-----------|----------|
| `.mjs` | ESM |
| `.cjs` | CommonJS |
| `.js` + `"type": "module"` | ESM |
| `.js` + `"type": "commonjs"` | CommonJS |

实际细节应以当前 Node 版本文档为准，但这张表足以覆盖常规面试与项目判断。

### 10.2 ESM 中没有 CommonJS 的模块变量

ESM 中不能直接使用：

```js
require
module
exports
__filename
__dirname
```

例如：

```js
// ESM
console.log(__dirname); // ReferenceError
```

可使用 `import.meta.url`：

```js
console.log(import.meta.url);
```

如果目标 Node 版本没有直接提供所需路径属性，可以从 URL 转换：

```js
import { fileURLToPath } from 'node:url';
import path from 'node:path';

const filename = fileURLToPath(import.meta.url);
const dirname = path.dirname(filename);
```

### 10.3 Node ESM 的相对路径

Node ESM 通常要求相对路径写出完整文件名：

```js
import { add } from './math.js';
```

不要默认依赖 CommonJS 风格的扩展名推断：

```js
import { add } from './math'; // Node ESM 中通常不能这样省略
```

这使 Node ESM 的模块说明符更接近 URL 的明确定位规则。

### 10.4 裸包名解析

```js
import express from 'express';
```

`express` 是裸模块说明符。Node 会根据包解析规则查找 `node_modules` 中的包，并结合包的 `package.json` 确定入口。

Node 内置模块建议使用 `node:` 前缀，表达来源更明确：

```js
import fs from 'node:fs';
import path from 'node:path';
```

CommonJS 也可以：

```js
const fs = require('node:fs');
```

### 10.5 `main`、`module` 与 `exports`

#### `main`

传统包入口：

```json
{
  "main": "./dist/index.cjs"
}
```

主要服务于 Node 和传统工具的包入口解析。

#### `module`

```json
{
  "module": "./dist/index.js"
}
```

`module` 是打包工具生态形成的惯例，通常指向 ESM 构建，但它不是 Node 包解析中与 `main` 完全同等级的通用标准字段。

#### `exports`

现代 Node 包可以使用 `exports` 精确声明公开入口：

```json
{
  "exports": {
    ".": "./dist/index.js",
    "./utils": "./dist/utils.js"
  }
}
```

使用方：

```js
import pkg from 'my-package';
import utils from 'my-package/utils';
```

`exports` 的作用：

- 声明包的公共入口。
- 限制用户访问未公开的内部文件。
- 支持子路径导出。
- 支持按条件选择不同构建。

### 10.6 条件导出

一个包可以给 `import` 和 `require` 提供不同入口：

```json
{
  "type": "module",
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

这样：

- ESM `import` 获得 ESM 文件。
- CommonJS `require` 获得 CJS 文件。

条件顺序和具体支持项会影响解析结果，发布库时应进行真实环境测试。

### 10.7 `imports` 字段

包内部可以通过 `imports` 定义私有映射，键通常以 `#` 开头：

```json
{
  "imports": {
    "#utils/*": "./src/utils/*.js"
  }
}
```

包内部：

```js
import { format } from '#utils/format.js';
```

它用于包内部别名或条件映射，不等同于给外部使用者声明公共子路径。

### 10.8 在 ESM 中加载 CommonJS

Node 通常允许 ESM 导入 CommonJS：

```js
// legacy.cjs
module.exports = {
  name: 'legacy'
};
```

```js
// app.mjs
import legacy from './legacy.cjs';

console.log(legacy.name);
```

CommonJS 的 `module.exports` 通常映射为 ESM 的默认导入。

某些情况下工具或 Node 还能通过静态分析提供类似命名导入：

```js
import { name } from './legacy.cjs';
```

但 CommonJS 导出高度动态，这种命名导入并不如默认导入稳定。兼容旧模块时更稳妥的方式通常是：

```js
import legacy from './legacy.cjs';
const { name } = legacy;
```

### 10.9 在 CommonJS 中加载 ESM

历史上，CommonJS 的同步 `require()` 不能直接加载需要异步求值的 ESM。最通用的跨版本方式是在 CommonJS 中使用动态导入：

```js
// app.cjs
async function main() {
  const module = await import('./modern.js');
  module.run();
}

main();
```

现代 Node 版本对 `require(esm)` 的支持范围在持续演进，但会受到同步模块图、顶层 `await`、版本和标志等限制。面试和跨版本代码中，更稳妥的回答仍是：

> CommonJS 需要加载 ESM 时优先使用异步 `import()`，并根据项目锁定的 Node 版本确认互操作能力。

### 10.10 双包问题 Dual Package Hazard

如果一个包同时发布 CJS 和 ESM，并且同一进程通过两种入口分别加载，可能产生两份模块实例：

```text
require('package')  → CJS 实例
import 'package'    → ESM 实例
```

可能导致：

- 单例状态不再唯一。
- `instanceof` 判断异常。
- 两边维护不同缓存。
- 配置或注册行为重复执行。

库作者需要谨慎设计条件导出和共享实现，使用者则应尽量在一个项目中统一导入方式。

### 10.11 JSON 与其他模块

CommonJS 传统上可以：

```js
const data = require('./data.json');
```

ESM 导入 JSON 往往需要导入属性，具体语法和支持程度取决于运行环境版本：

```js
import data from './data.json' with { type: 'json' };
```

旧资料中可能看到 `assert { type: 'json' }`。这是早期导入断言语法；现代标准与运行环境逐步转向 import attributes 的 `with` 写法。实际项目应以目标 Node、浏览器和构建工具版本为准。

CSS、Wasm、图片等导入也不是所有 JavaScript 环境都统一支持。看到下面代码时：

```js
import './style.css';
import logo from './logo.png';
```

通常意味着构建工具或框架提供了额外处理，不应误认为这是所有原生 ESM 环境共有的 JavaScript 语义。

### 10.12 Node 模块系统面试回答模板

> Node 同时支持 CommonJS 和 ESM。`.cjs` 明确是 CommonJS，`.mjs` 明确是 ESM，`.js` 通常由最近 package.json 的 type 字段决定。ESM 没有 require、module、exports、__filename 和 __dirname，通常使用 import.meta.url。现代包可通过 exports 声明公共入口和条件导出，分别服务 import 与 require。ESM 加载 CommonJS 时通常把 module.exports 视作默认导出；CommonJS 加载 ESM 时，为了兼容不同 Node 版本，通常使用动态 import()。

## 11. 打包工具时代的模块化

### 11.1 为什么有了 ESM 还需要打包工具

现代浏览器已经能直接运行 ESM，但工程项目仍经常需要打包工具，因为它们还解决：

- npm 裸包名解析。
- TypeScript、JSX、Vue SFC 等源码转换。
- 兼容旧浏览器。
- CSS、图片、字体等资源处理。
- Tree Shaking。
- 代码压缩和哈希文件名。
- Code Splitting 与懒加载。
- 开发服务器、热更新和生产优化。

因此，模块系统负责表达依赖关系；打包工具利用这些关系构建和优化整个应用。

### 11.2 模块依赖图

从入口文件开始，工具分析每个静态或动态依赖：

```text
src/main.js
├── src/app.js
│   ├── src/api.js
│   └── src/components/button.js
├── src/style.css
└── node_modules/library/index.js
```

这张图可以用来：

- 确定哪些文件需要进入构建。
- 识别共享依赖。
- 移除未使用代码。
- 按动态导入点拆分 chunk。
- 计算资源加载顺序。

### 11.3 Bundle 是什么

打包工具可能把多个源模块转换成较少的输出文件：

```text
源文件：
main.js + app.js + api.js + button.js

构建结果：
assets/index-a1b2c3.js
```

输出并不一定只有一个文件。现代构建通常会产生：

- 入口 chunk。
- 共享 vendor chunk。
- 动态导入 chunk。
- CSS 和其他资源文件。

“打包”不等于“所有代码永远塞进一个文件”。

### 11.4 Webpack、Rollup、Vite 的定位

#### Webpack

- 以模块依赖图为核心的综合打包工具。
- 支持多种资源与 loader/plugin 生态。
- 擅长复杂应用构建、代码分割和广泛兼容。
- 历史生态非常成熟。

#### Rollup

- 以 ESM 为核心设计。
- 输出结构通常更简洁。
- Tree Shaking 能力突出。
- 经常用于 JavaScript 库打包。

#### Vite

- 是现代前端开发与构建工具，不只是一个打包器名称。
- 开发环境利用浏览器原生 ESM 按需提供模块。
- 依赖预构建可以处理性能与兼容问题。
- 生产构建使用成熟的构建管线，并随版本演进。

不要把三者简单理解成严格的替代关系。它们的定位、生态和适用场景不同。

### 11.5 Vite 为什么开发启动快

传统开发打包器在启动时可能先构建完整依赖图并生成 bundle，项目越大，首次构建越慢。

Vite 开发环境主要思路：

1. 浏览器请求入口模块。
2. 开发服务器按请求转换并返回对应模块。
3. 浏览器根据 ESM 导入继续请求依赖。
4. 未被访问的业务模块暂时不需要全部处理。

```text
浏览器请求 /src/main.js
       ↓
Vite 转换 main.js
       ↓
浏览器发现 import './App.vue'
       ↓
继续按需请求 App.vue
```

这减少了开发服务器启动时必须处理的业务模块数量。

### 11.6 依赖预构建

开发环境中，第三方依赖可能：

- 仍使用 CommonJS 或 UMD。
- 内部包含大量细碎 ESM 文件，造成过多请求。
- 导出格式与浏览器原生 ESM 不完全匹配。

Vite 会对某些依赖进行预构建，把它们转换、合并为更适合开发服务器提供的 ESM 形式。

因此，“Vite 开发环境完全不处理依赖，原样交给浏览器”也是不准确的。

### 11.7 Tree Shaking

Tree Shaking 指构建时移除未被使用的导出代码。

```js
// math.js
export function add(a, b) {
  return a + b;
}

export function subtract(a, b) {
  return a - b;
}
```

```js
// app.js
import { add } from './math.js';

console.log(add(1, 2));
```

如果分析确认 `subtract` 没有被使用，也没有必须保留的副作用，生产构建可能将它删除。

#### Tree Shaking 需要什么

- 可静态分析的模块结构，通常是 ESM。
- 构建工具识别使用关系。
- 压缩阶段删除不可达或无用代码。
- 正确判断模块和语句是否有副作用。

#### Tree Shaking 不等于 ESM 自动删除代码

浏览器原生运行 ESM 时，不会因为某个导出没被导入就自动删掉源码。Tree Shaking 通常是构建工具执行的优化。

ESM 提供的是静态分析基础，而不是自动压缩行为。

### 11.8 副作用 Side Effects

副作用是指模块在导出值之外对外部环境产生影响：

```js
console.log('模块执行');
window.appReady = true;
document.body.classList.add('loaded');
```

即使没有使用它的导出，构建工具也不能随意删除这个模块，因为执行本身有意义。

纯模块：

```js
export function add(a, b) {
  return a + b;
}
```

有副作用模块：

```js
registerGlobalPlugin();
export const plugin = {};
```

### 11.9 `package.json` 的 `sideEffects`

包作者可以声明文件是否包含副作用：

```json
{
  "sideEffects": false
}
```

意思是包内模块可被视为没有导入级副作用，未使用模块可以更大胆地删除。

如果部分文件有副作用：

```json
{
  "sideEffects": [
    "*.css",
    "./src/polyfill.js"
  ]
}
```

错误地写 `false` 可能导致必要初始化或样式在生产构建中被删除。

`sideEffects` 与函数注释中的纯调用标记不是完全相同的概念：前者通常描述文件/模块是否有副作用，后者帮助压缩器判断某次函数调用是否可删除。

### 11.10 Code Splitting

代码分割是把应用拆成多个可独立加载的 chunk，而不是一次加载全部代码。

最常见的分割点是动态导入：

```js
async function openAdminPage() {
  const { renderAdmin } = await import('./admin.js');
  renderAdmin();
}
```

构建工具可能输出：

```text
index.js
admin-8f3a.js
```

用户没有进入管理页面时，就不必立即下载管理模块。

常见场景：

- 路由懒加载。
- 大型编辑器或图表库。
- 后台管理功能。
- 低频弹窗。
- 多语言资源。

### 11.11 懒加载不是越多越好

拆分过细会带来：

- 更多网络请求和调度开销。
- 用户点击后才开始等待。
- chunk 之间产生复杂依赖。
- 缓存策略和错误处理更复杂。

通常应根据首屏性能、模块体积、使用频率和网络条件决定拆分边界。

### 11.12 预加载与预取

动态模块可以结合资源提示优化加载体验：

- `modulepreload`：提前加载预计很快会用到的模块及相关处理。
- `preload`：高优先级获取当前页面需要的资源。
- `prefetch`：浏览器空闲时获取未来可能使用的资源，优先级通常较低。

```html
<link rel="modulepreload" href="/assets/feature.js">
```

它们只影响资源获取策略，不会替代模块系统本身的依赖和执行规则。

### 11.13 Source Map 与模块调试

打包后，浏览器运行的是构建产物，而不是原始文件。Source Map 建立生成代码与源码的映射，使开发者工具可以：

- 显示原文件和行号。
- 在 TypeScript 或压缩前源码中断点。
- 把错误堆栈映射回源码。

生产环境是否公开 Source Map，需要权衡调试能力、源码暴露和监控平台上传方式。

### 11.14 Module Federation

Webpack Module Federation 等机制允许一个独立构建在运行时加载另一个构建暴露的模块：

```text
Host 应用
  ├── 本地模块
  └── 运行时加载 Remote 应用暴露的组件
```

它常用于大型前端或微前端场景，解决跨构建共享模块的问题。

需要同时处理：

- 远程入口版本。
- 共享依赖与单例。
- 加载失败降级。
- 部署和缓存策略。
- 团队间接口契约。

它属于模块化的工程扩展，不是 ECMAScript 模块语法本身。

## 12. 如何设计一个好的模块

### 12.1 单一职责

一个模块应围绕清晰职责组织：

```text
user-api.js      负责用户请求
user-store.js    负责用户状态
user-format.js   负责用户数据格式化
```

避免创建职责混杂的 `utils.js`，不断加入互不相关的方法。

### 12.2 明确公共接口

只导出使用者真正需要的能力：

```js
function normalizeUser(raw) {
  // 内部实现，不导出
}

export async function getUser(id) {
  const raw = await request(`/users/${id}`);
  return normalizeUser(raw);
}
```

公共接口越小，内部重构空间越大。

### 12.3 降低模块耦合

强耦合：

```js
import globalStore from '../app/global-store.js';
import router from '../app/router.js';

export function save() {
  // 同时操作多个全局单例
}
```

依赖注入：

```js
export function createSaver({ store, navigate }) {
  return function save() {
    // 依赖由外部传入
  };
}
```

依赖注入可以：

- 让依赖更明确。
- 降低底层模块对应用层的反向依赖。
- 更容易测试。
- 减少循环依赖。

### 12.4 避免导入即执行重副作用

不推荐：

```js
// analytics.js
connect();
startTimer();
window.addEventListener('click', track);
```

只要导入就自动执行，调用者很难控制生命周期。

更可控：

```js
export function startAnalytics() {
  connect();
  startTimer();
  window.addEventListener('click', track);

  return function stop() {
    window.removeEventListener('click', track);
  };
}
```

并非所有副作用都错误，但应该显式、可预测并便于清理。

### 12.5 避免循环依赖

依赖方向最好保持单向：

```text
页面层 → 业务层 → 数据层 → 基础工具层
```

基础工具层不应再导入页面层。发现循环时先问：

- 是否有共同逻辑可以提取？
- 是否把组合职责放错了层？
- 是否可以通过参数传入回调？
- 是否因为聚合入口造成了间接循环？

### 12.6 默认导出还是命名导出

默认导出：

```js
export default function createUser() {}
```

优点：导入简洁，适合模块只有一个主能力。

风险：使用方可以任意命名，不同文件中名称可能不一致，重构搜索相对困难。

命名导出：

```js
export function createUser() {}
export function deleteUser() {}
```

优点：名称统一，自动补全和重构更明确，适合工具集合或多个公共能力。

没有绝对规则。团队应保持一致，并根据模块职责选择。

### 12.7 模块状态与单例

模块只执行一次通常使顶层状态具有单例效果：

```js
let currentUser = null;

export function setCurrentUser(user) {
  currentUser = user;
}

export function getCurrentUser() {
  return currentUser;
}
```

这种方式简单，但也会带来共享可变状态和测试隔离问题。

需要多个独立实例时，导出工厂函数：

```js
export function createUserStore() {
  let currentUser = null;

  return {
    set(user) {
      currentUser = user;
    },
    get() {
      return currentUser;
    }
  };
}
```

### 12.8 模块设计检查表

- 模块职责能否用一句话说明？
- 导出的 API 是否足够小？
- 是否存在导入即执行的隐藏副作用？
- 是否依赖不必要的全局状态？
- 依赖方向是否清晰、是否成环？
- 是否真的需要默认导出？
- 是否把内部实现意外暴露成公共 API？
- 是否需要懒加载，还是静态导入更合适？
- 是否能在测试中替换依赖或创建独立实例？

## 13. 高频面试题

### 13.1 什么是模块化，它解决了什么问题

回答要点：

- 将复杂程序拆分为职责明确的单元。
- 为每个模块提供独立作用域。
- 控制私有实现和公共 API。
- 显式表达模块依赖。
- 让模块可以复用、替换、测试和按需加载。
- 降低全局污染、命名冲突和维护成本。

### 13.2 JavaScript 模块化经历了什么演进

回答顺序：

```text
全局脚本
→ 命名空间
→ IIFE
→ CommonJS（服务端）与 AMD/CMD（浏览器）
→ UMD 兼容
→ ESM 语言标准
→ 原生 ESM 与现代构建工具生态
```

### 13.3 `exports` 与 `module.exports` 有什么区别

```js
exports === module.exports; // 模块初始化时为 true
```

`exports` 是初始别名，Node 最终返回 `module.exports`。可以给 `exports` 添加属性，但不能用重新赋值的方式替换最终导出：

```js
exports.a = 1;             // 有效
exports = { a: 1 };        // 无效，断开别名
module.exports = { a: 1 }; // 有效
```

### 13.4 为什么重复 require 不会重复执行

模块第一次加载前后会进入缓存。以后解析到相同模块标识时，`require` 直接返回缓存中的 `module.exports`。

缓存还使 CommonJS 能在循环依赖时返回正在执行模块的部分导出。

### 13.5 为什么 ESM 的 import 必须写在顶层

静态结构使引擎和工具可以在代码执行前构建依赖图、校验导出并建立绑定，也让 Tree Shaking 成为可能。需要条件或按需加载时，应使用 `import()`。

### 13.6 ESM 导入值能修改吗

不能重新赋值导入绑定：

```js
import { count } from './counter.js';
count = 1; // 不允许
```

但如果导入的是对象，可以按普通对象规则修改其属性，除非对象被冻结或接口另有限制：

```js
import { state } from './store.js';
state.count = 1;
```

### 13.7 Tree Shaking 为什么依赖 ESM

因为 ESM 的静态导入导出可在执行前分析。CommonJS 的依赖路径和导出对象可以动态变化，因此工具难以准确确认哪些代码未被使用。

Tree Shaking 还依赖正确的副作用分析，并不是只要写 ESM 就一定能删除所有无用代码。

### 13.8 `import()` 和静态 import 的区别

- 静态 import 是声明，位于模块顶层，在执行前参与模块链接。
- `import()` 是返回 Promise 的表达式，可以运行时调用。
- 静态 import 适合核心依赖。
- `import()` 适合条件加载和代码分割。

### 13.9 ESM 如何处理循环依赖

ESM 在实例化阶段先建立导入导出的 live binding，再按照依赖图求值。如果读取时目标变量已经初始化，可以正常工作；如果在 `let`、`const`、`class` 初始化前读取，会触发 TDZ 的 `ReferenceError`。

### 13.10 输出题：CommonJS 基本类型

```js
// a.cjs
let count = 0;

function increment() {
  count += 1;
}

module.exports = {
  count,
  increment
};
```

```js
// main.cjs
const a = require('./a.cjs');

a.increment();
console.log(a.count);
```

输出：

```text
0
```

原因：导出对象的 `count` 属性在创建时获得数字 `0`，之后内部变量变化不会自动更新该属性。

### 13.11 输出题：ESM live binding

```js
// a.js
export let count = 0;

export function increment() {
  count += 1;
}
```

```js
// main.js
import { count, increment } from './a.js';

increment();
console.log(count);
```

输出：

```text
1
```

原因：导入的 `count` 是指向导出变量的 live binding。

### 13.12 输出题：exports 断开引用

```js
// a.cjs
exports.a = 1;
module.exports = { b: 2 };
exports.c = 3;
```

```js
console.log(require('./a.cjs'));
```

输出：

```js
{ b: 2 }
```

`module.exports` 被替换后，`exports` 仍指向旧对象。

### 13.13 输出题：模块只执行一次

```js
// a.js
console.log('a');
export const value = 1;
```

```js
// main.js
import './a.js';
```

输出一次：

```text

```

同一模块在同一个模块图中通常只求值一次。

### 13.14 场景题：路由为什么使用动态导入

```js
const routes = [
  {
    path: '/admin',
    component: () => import('./pages/Admin.js')
  }
];
```

回答要点：

- 管理页面不进入首屏静态依赖主体。
- 构建工具可以创建独立 chunk。
- 用户访问路由时再下载。
- 降低首屏 JavaScript 体积。
- 需要同时处理加载状态和失败重试。

### 13.15 场景题：模块循环依赖如何排查

1. 查看构建工具警告和模块依赖图。
2. 查找顶层立即读取的导入变量。
3. 检查 `index.js` 聚合入口形成的间接环。
4. 抽取双方共同依赖到第三个模块。
5. 调整分层，让依赖方向保持单向。
6. 必要时用依赖注入或延迟函数调用解环。

## 14. 常见误区

### 14.1 拆文件就是模块化

拆文件只是物理组织。没有作用域隔离、接口控制、依赖声明和加载机制，仍不算完整模块化。

### 14.2 CommonJS 只会复制值

`require` 返回 `module.exports`。基本类型看起来像快照，对象仍按引用共享。它与 ESM live binding 的差异不能只用“拷贝/引用”四个字概括。

### 14.3 ESM 的 import 是异步函数

静态 `import` 是声明，不返回 Promise，也不是运行到该行才调用的函数。动态 `import()` 才是返回 Promise 的表达式。

### 14.4 ESM 有 Tree Shaking，所以浏览器会自动删代码

ESM 只是提供静态结构。Tree Shaking 一般由打包和压缩工具在构建时执行。

### 14.5 模块对象只读，所以内部对象不可变

导入绑定不能重新赋值，不代表导入对象自动深度冻结。是否可修改属性由对象本身和 API 设计决定。

### 14.6 模块缓存意味着永远只有一个实例

不同解析路径、不同 URL、不同模块系统入口、不同进程或不同运行上下文都可能产生不同实例。双包问题就是典型例子。

### 14.7 能处理循环依赖，所以循环依赖没有问题

CommonJS 和 ESM 都有处理机制，但循环仍可能暴露部分导出、触发 TDZ、造成初始化顺序耦合。工程上应优先重构。

### 14.8 UMD 是 ESM 之前的统一标准

UMD 是同时兼容 AMD、CommonJS 和全局变量的包装模板，不是 JavaScript 语言原生模块标准。

### 14.9 `package.json` 的 module 是 Node 标准 ESM 入口

`module` 主要是工具生态惯例；现代 Node 包对公共入口和条件导出更应关注 `exports`。

### 14.10 导入 CSS 和图片属于标准 ESM

这通常是构建工具或特定运行环境扩展，不是所有 JavaScript ESM 环境都支持的统一行为。

## 15. 最短复习版

### 15.1 演进路线

```text
全局变量污染、依赖顺序混乱
  ↓
命名空间：减少全局变量，但没有私有成员
  ↓
IIFE：函数作用域 + 闭包，实现私有成员和公共接口
  ↓
CommonJS：服务端同步 require，module.exports，模块缓存
AMD/CMD：浏览器异步加载
  ↓
UMD：兼容 CJS、AMD 和浏览器全局
  ↓
ESM：语言标准，静态结构，live binding
  ↓
Node ESM、浏览器原生 ESM、现代构建工具
```

### 15.2 CommonJS 必背

- 一个文件一个模块，Node 使用函数包装形成作用域。
- `exports` 是 `module.exports` 的初始别名。
- 最终返回的是 `module.exports`。
- `require` 是运行时同步调用，可以动态使用。
- 模块第一次执行后进入缓存。
- 循环依赖得到当前已执行部分的导出。
- 动态结构不利于 Tree Shaking。

### 15.3 ESM 必背

- `import`、`export` 是语言原生语法。
- 静态 import 位于顶层，可在执行前分析和链接。
- 模块有独立作用域，自动严格模式，顶层 `this` 是 `undefined`。
- 命名导入是只读 live binding。
- `import()` 返回 Promise，用于按需加载和代码分割。
- 循环依赖先建立绑定，提前读取可能触发 TDZ。
- 浏览器 `type="module"` 默认延迟执行，遵守 CORS。
- 静态结构使 ESM 更适合 Tree Shaking。

### 15.4 CJS 与 ESM 一句话对比

> CommonJS 在执行时通过 require 获取 module.exports，灵活但难以静态分析；ESM 在执行前通过静态 import/export 建立模块图和实时绑定，更适合浏览器原生模块与现代构建优化。

### 15.5 五个最高频问题

1. `exports` 和 `module.exports` 有什么区别？
2. CommonJS 与 ESM 有哪些区别？
3. ESM live binding 是什么？
4. 为什么 ESM 更适合 Tree Shaking？
5. CommonJS 和 ESM 分别如何处理循环依赖？

### 15.6 完整面试回答

> JavaScript 最初通过多个 script 标签组织代码，但所有脚本共享全局作用域，存在命名冲突、依赖不明确和加载顺序问题。命名空间只能减少全局变量，IIFE 才利用函数作用域和闭包实现私有成员与公共接口，但依赖仍靠手工管理。后来服务端出现 CommonJS，通过 require 和 module.exports 同步加载并缓存模块；浏览器端因为网络加载需要，出现 AMD、CMD，UMD 则用于兼容多种环境。最终 ES6 提供语言原生的 ESM，通过静态 import/export 在执行前构建并链接模块图，命名导出使用 live binding，也更利于 Tree Shaking。现代项目一般以 ESM 为主，通过浏览器、Node 或 Vite、Webpack、Rollup 等工具运行和构建。

## 16. 复习建议

1. **理解问题**：全局脚本有什么缺陷，命名空间和 IIFE 分别解决了什么。

3. **掌握核心**：重点掌握 CommonJS、ESM 以及两者的加载、导出和循环依赖差异。
4. **联系工程**：理解 Node 双模块系统、Tree Shaking、`sideEffects`、动态导入和代码分割。
