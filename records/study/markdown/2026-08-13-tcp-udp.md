## 一、TCP 可靠传输机制

### 1.1 字节流模型
- TCP 眼里只有「一串连续的字节」，每个字节有全局序列号
- seq = 本报文第一个字节的位置；ack = 期望收到的下一个字节序号 = 已收字节数 + 1

### 1.2 累积确认（Cumulative ACK）
- 只有 ACK 没有 NACK；ack=N 隐含「N 之前全部收到」
- 一个 ACK 可覆盖多个报文 → ACK 数量远少于数据报文
- 乱序到达 → 接收方立即重复回「期望序号」的 ACK → 这是快速重传的丢包信号

### 1.3 重传机制
| 机制 | 触发 | 要点 |
|------|------|------|
| 超时重传 | RTO 超时 | RTO 由 RTT 动态估算（SRTT + 4×RTTVAR），重传后 RTO 翻倍（指数退避）；超上限（Linux 15 次）放弃连接 |
| 快速重传 | 收到 3 个重复 ACK | 不等超时立即重传；1 个重复 ACK 可能只是乱序，3 个基本断定丢包 |
| SACK | 接收方带 SACK 块 | 告知「哪些区间收到」，只重传缺失部分（否则 Go-Back-N 式重复重传） |

### 1.4 其他
- 校验和：坏包丢弃，靠超时重传兜底
- TCP 无法感知对端存活 → 需要应用层心跳（WebSocket 章节伏笔）

### 1.5 与 QUIC 呼应
- TCP ACK 确认字节序号、重传复用原序号（重传歧义，RTT 不准）；QUIC 确认包号、重传用新号（RTT 精确）

## 二、流量控制 vs 拥塞控制

### 2.1 两个窗口（核心）
| | 接收窗口 rwnd | 拥塞窗口 cwnd |
|--|--------------|--------------|
| 回答的问题 | 接收方能收多少 | 网络能扛多少 |
| 由谁决定 | 接收方（ACK 里通告） | 发送方自己维护（丢包反馈） |
| 防止什么 | 接收方缓冲区溢出 | 网络过载 |

**发送窗口 = min(rwnd, cwnd)**

### 2.2 流量控制细节
- 窗口通告：rwnd=0 时发送方必须停发
- 窗口更新死锁：更新报文丢失 → 发送方等窗口、接收方等数据 → **坚持定时器 + 窗口探测包**（发 1 字节逼对方重新通告）
- **Nagle 算法**：同一时刻只允许一个未确认小报文，小数据攒着合并（防小包风暴）
- **延迟确认**：延迟 ~200ms 或攒 2 个段回 ACK（减少 ACK 数量）
- **Nagle × 延迟确认互锁**：发送方被 Nagle 卡住 + 接收方延迟 ACK → 互相等 → ~40ms 随机延迟；低延迟场景关 Nagle（TCP_NODELAY）

### 2.3 拥塞控制四阶段
| 阶段 | 触发 | 行为 |
|------|------|------|
| 慢启动 | 连接建立/超时后 | cwnd 从 1 起，每 RTT 翻倍（指数探测带宽） |
| 拥塞避免 | cwnd ≥ ssthresh | 每 RTT +1（线性，接近容量时谨慎） |
| 快速恢复 | 3 个重复 ACK | cwnd 减半，线性增长，不退回慢启动 |
| 超时 | RTO 超时 | cwnd=1，ssthresh=cwnd/2，重新慢启动 |

**面试必答**：3 个重复 ACK 只减半因为链路还通（数据在流动），轻微拥塞；超时说明 ACK 都回不来（严重拥塞），必须归 1 重新探测。

**演进**：Tahoe（任何丢包都回慢启动）→ Reno（重复 ACK 快速恢复）→ CUBIC（按时间增长，Linux 默认）→ BBR（按带宽延迟积 BDP 建模，不看丢包）

### 2.4 一句话
> 流量控制管「对方」（rwnd 对方通告）；拥塞控制管「路上」（cwnd 自己摸索）。

## 三、三次握手

### 3.1 流程与 seq/ack 值
```
① 客户端 SYN(seq=x)                      客户端: CLOSED → SYN_SENT
② 服务端 SYN+ACK(seq=y, ack=x+1)         服务端: LISTEN → SYN_RCVD
③ 客户端 ACK(seq=x+1, ack=y+1)           双方 → ESTABLISHED
```
- 第 ③ 步可捎带应用层数据（省一次 RTT，合法优化）

### 3.2 为什么是三次（三个层次）
1. **确认全双工收发能力**：双方都确认「我能发你也能收」
2. **同步双方 ISN**：序列号寻址的基础，双方起点必须互知。
   - ① 让服务端知道 x；② 让客户端知道 y 且服务端确认 x；③ 让服务端确认「客户端收到了 y」
   - 两次握手 → 服务端的 y 从未被确认，② 丢了服务端也不知道
3. **客户端拦截历史失效连接**：服务端无状态、认不出旧 SYN；只有发起方（客户端）能区分新旧 → 通过校验 ack（期望 = 自己最新 SYN seq + 1，对不上 → RST）行使否决权
   - 场景：SYN(seq=100) 迟到，客户端已重试 SYN(seq=200) 建立连接 A；旧 SYN 到达服务端，服务端回 SYN+ACK(seq=600, ack=101)；客户端收到发现 ack≠201 → 发 RST → 服务端清理半连接
   - 两次握手 → 服务端直接建立幽灵连接白占资源
   - RFC 793：CLOSED 状态收到非 SYN 包也回 RST

### 3.3 第三次握手丢失
- 客户端可能直接发数据 → 数据包携带的 ACK **隐式完成握手**（Linux 在 SYN_RCVD 收到合法 ACK 即 ESTABLISHED）
- 否则服务端停留在 SYN_RCVD，超时重传 SYN+ACK（默认 ~5 次，指数退避 1s/2s/4s...），耗尽后关闭

### 3.4 SYN Flood 与防御
**攻击原理**：伪造源 IP 的海量 SYN → 服务端为每个分配 TCB 入半连接队列 → 等 ACK 等到超时 → 队列塞满，正常用户进不来（资源不对称攻击）

**SYN Cookie（核心）**：
- 收到 SYN **不分配任何资源**，只算 cookie 塞进 SYN+ACK 的 seq
- `cookie = hash(四元组 + 服务端密钥) ⊕ 时间计数器(24bit) ⊕ MSS 编码(6bit)`
- 收到 ACK 时重算校验 + 检查时间窗口 → 合法才分配 TCB
- 攻不破：伪造 IP 收不到 SYN+ACK 回不了合法 ACK；有密钥无法伪造；时间窗口防重放
- **代价**：无法协商 TCP 选项（SACK/时间戳/窗口缩放丢失，只能编码 MSS）→ 高带宽长链路性能下降；每次 SYN 有 CPU 开销
- Linux 默认 tcp_syncookies=1：队列溢出时才启用（平时保留选项协商）

**分层防御**：网络层（BCP38 入站过滤、黑洞路由、CDN 清洗）→ 系统层（tcp_max_syn_backlog 扩容、tcp_synack_retries 调小）→ SYN Cookie → SYN Proxy（防火墙代答，验证通过才连后端）→ 限速

### 3.5 连接队列（后端高频）
- 半连接队列 SYN Queue：收到 SYN 未完成握手
- 全连接队列 Accept Queue：握手完成等 accept()（backlog 控制）
- 全连接队列溢出 → 连接被丢弃/客户端重传 —— 压测大量连接超时先查它

## 四、四次挥手

### 4.1 流程与状态
```
① 主动方 FIN(seq=u)                      主动方: FIN_WAIT_1
② 被动方 ACK(ack=u+1)                    被动方: CLOSE_WAIT / 主动方: FIN_WAIT_2
③ 被动方 FIN(seq=v)（数据发完后）          被动方: LAST_ACK
④ 主动方 ACK(ack=v+1)                    被动方: CLOSED / 主动方: TIME_WAIT(2MSL) → CLOSED
```

### 4.2 为什么四次 vs 三次
- 全双工，两个方向独立关闭；被动方可能还有数据要发
- FIN 只表示「我不再发了」，ACK 和 FIN 被必然拆开（握手时 SYN+ACK 合并是因为天然同一件事）

### 4.3 什么时候合并成三次
- 被动方恰好没数据要发：ACK+FIN 捎带同包（Piggyback）
- 或延迟确认：收到 FIN 延迟 ~200ms，期间应用也 close 了 → 一起发

### 4.4 TIME_WAIT 为什么是 2MSL（两个原因）
1. **保证最后一个 ACK 可达**：ACK 丢了被动方会重发 FIN，主动方需留在 TIME_WAIT 重发 ACK，否则被动方卡 LAST_ACK
2. **让旧连接报文在网络中消亡**：2MSL = 报文最大生存时间 × 2，保证同四元组的新连接不会被旧连接的迟到包污染

### 4.5 排查
- **服务端大量 CLOSE_WAIT**：收到 FIN 已回 ACK 但应用没 close() —— 代码泄漏（异常分支没关、响应慢超时、阻塞 I/O）→ `ss -tan | grep CLOSE_WAIT` 定位进程。**本质是应用层 bug，不是内核参数**
- **客户端大量 TIME_WAIT**：短连接高并发频繁主动关闭 → 端口耗尽。优化：长连接/连接池、SO_REUSEADDR、tcp_tw_reuse（配时间戳，仅出站）、调低 MSL

### 4.6 半关闭
shutdown(fd, SHUT_WR) 只关发送方向保留接收 —— 即 FIN_WAIT_2 阶段状态

## 五、TCP vs UDP

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠、有序、不重复 | 不可靠、可能乱序/丢失 |
| 传输单位 | 字节流（无边界） | 数据报（有边界） |
| 头部 | 20~60 字节 | 8 字节（源/目的端口、长度、校验和各 2B） |
| 流控/拥控 | 有 | 无 |
| 场景 | HTTP、文件、邮件 | 音视频、DNS、游戏、QUIC 底座 |

记忆：TCP 牺牲效率换可靠，UDP 牺牲可靠换低延迟；DNS 默认 UDP，响应超 512 字节切 TCP；音视频丢帧可接受、延迟不可接受。

## 七、误区纠正记录

| # | 错误理解 | 正确模型 |
|---|---------|---------|
| 1 | 握手第 3 步必须发纯 ACK | 可捎带应用层数据（合法优化），但标准流程先讲纯 ACK |
| 2 | 挥手只知道流程 | 需补状态机（FIN_WAIT_1/2、CLOSE_WAIT、LAST_ACK）与「为什么四次」论证 |
| 3 | TIME_WAIT 只有「等 ACK」一个原因 | 还有「旧报文消亡防四元组污染」 |
| 4 | CLOSE_WAIT 多靠内核调优 | 是应用层未 close() 的代码 bug |
| 5 | 握手中服务端能识别旧 SYN | 服务端无状态认不出，只能靠客户端校验 ack 发 RST |
| 6 | SYN Cookie 无代价 | 丢失 TCP 选项协商（SACK/时间戳/窗口缩放），高 BDP 场景性能下降 |
