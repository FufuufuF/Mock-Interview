## 一、DNS 解析完整链路

### 1.1 六个检查点（查询路径，非 6 次网络请求）

```
① 浏览器 DNS 缓存（零网络开销）
② 操作系统：hosts 文件（最高优先级）→ 系统 DNS 缓存
────────────────────────── 以上全为本地检查 ──────────────────────
③ 本地 DNS 服务器（LDNS）← 客户端唯一的网络请求（递归）
    ↓ 迭代查询（本地 DNS 发出）
④ 根服务器（.）       → 指路：.com 服务器在哪
⑤ 顶级域服务器(.com)  → 指路：google.com 权威服务器在哪
⑥ 权威服务器          → 返回最终 IP
```

**关键**：根服务器和顶级域服务器不存具体域名，只负责「指路」（存下一级服务器地址）；客户端视角只发了一个请求（给本地 DNS），后面 3 层由本地 DNS 代跑。

### 1.2 递归 vs 迭代（必背）

| 方向 | 类型 | 定义 |
|------|------|------|
| 客户端 → 本地 DNS | **递归** | 全权委托，一个请求一个最终答案 |
| 本地 DNS → 根/顶级/权威 | **迭代** | 自己逐级问，每层只指路 |

记忆：**递归 = 委托代办；迭代 = 自己跑腿逐级问**。
「逐级询问下一级」正是迭代查询的定义（本人曾把两者弄反）。

### 1.3 缓存层级与 TTL

| 缓存层 | TTL 特点 |
|--------|---------|
| 浏览器缓存 | 短（几十秒~分钟） |
| 系统缓存 + hosts | hosts 永远优先 |
| 本地 DNS 服务器 | 遵循权威服务器下发的 TTL（秒~天） |
| 权威服务器 | 管理员配置 TTL |

- TTL 小：变更生效快，查询压力大；TTL 大：解析快，故障转移慢
- 换 IP 后用户仍访问旧地址 = 各级缓存未过期

## 二、DNS 前端优化

### 2.1 四个资源提示（两组，别混）

| 指令 | 做什么 | 备注 |
|------|--------|------|
| `dns-prefetch` | 提前解析域名→IP | 最廉价，空闲时做 |
| `preconnect` | DNS + TCP + TLS 全建好 | 占用连接，别滥用 |
| `preload` | 当前页马上要用的资源 | 高优先级（首屏字体/CSS） |
| `prefetch` | 未来可能用的资源 | 低优先级，空闲下载 |

**注意**：preload/prefetch 是「下载资源」，dns-prefetch/preconnect 是「准备连接」，两组不同维度的优化。

### 2.2 域名收敛 vs 拆分
- 收敛：减少 DNS 查询，配合 HTTP/2 多路复用一个连接搞定
- 拆分（cookie-free domain）：静态资源独立域名不携带 Cookie、方便 CDN；HTTP/2 时代趋势是收敛

## 三、浏览器缓存

### 3.1 整体流程

```
强缓存命中（未过期）→ 200 (from cache)，不发请求
强缓存失效 → 带条件头请求（If-Modified-Since / If-None-Match）
    ├─ 协商命中 → 304（只回响应头，无 body），复用本地副本
    └─ 未命中 → 200 + 新资源
```

### 3.2 强缓存
- **Expires**（HTTP/1.0）：绝对时间，客户端时钟不准会出错
- **Cache-Control**（**HTTP/1.1 引入**，优先级高于 Expires）：
  - `max-age=31536000`：相对时间
  - `no-cache`：用前必须向服务器验证（可缓存副本，走协商）——不是「不缓存」
  - `no-store`：完全不缓存（敏感数据）
  - `public`（中间层可缓存）/ `private`（仅浏览器缓存）
  - `immutable`：缓存期内内容绝不变（配 hash 文件名，跳过协商）
  - `s-maxage`：CDN/代理专用过期时间

### 3.3 协商缓存
| | Last-Modified | ETag |
|--|---------------|------|
| 值 | 最后修改时间（秒级精度） | 内容哈希/版本号 |
| 请求头 | If-Modified-Since | If-None-Match |
| 缺点 | 秒级精度不够；内容没变但时间变了误判 | 计算哈希有开销；依赖服务器实现（如 nginx 默认不生成） |

- **两者同时存在 ETag 优先**（更精确）
- 命中 → 304（只回响应头不回 body，省流量）；未命中 → 200 + 新资源
- 协商缓存的前提：客户端带条件请求头，没有则服务器无从判断

### 3.4 缓存位置
Memory Cache（内存，关标签页即失）→ Disk Cache（磁盘，持久）→ Service Worker Cache（可编程，PWA）→ Push Cache（已边缘化）
**优先级**：Service Worker → Memory → Disk → 网络

### 3.5 常见坑
- 强缓存命中显示 `200 (from disk cache)`，**不是 304**（304 说明发过请求）
- 后退/前进用 bfcache 可能不重新执行 JS
- F5 对 HTML 走协商；Ctrl+F5 强制刷新跳过强缓存

## 四、缓存策略设计（标准答案）

```
HTML 页面：   Cache-Control: no-cache          → 每次验证，保证拿到最新页面
JS/CSS/图片： Cache-Control: max-age=31536000, immutable + 文件名带内容 hash
```

- **hash 变了 = 文件名变了 = 新缓存条目**，老缓存自动作废
- HTML 是入口必须新鲜；静态资源是内容可以死缓存
- **用 URL 变化代替缓存失效** = 整套设计灵魂
- CDN 场景：HTML 源站 no-cache（或 s-maxage 很短），静态资源 max-age 一年

## 六、误区纠正记录

| # | 错误理解 | 正确模型 |
|---|---------|---------|
| 1 | 本地 DNS 叫「本地 CDN」 | 是 LDNS（本地 DNS 服务器），CDN 是内容分发网络，两码事 |
| 2 | 本地 DNS 对上是递归查询 | 客户端→本地 DNS 是递归；本地 DNS→根/顶级/权威是迭代（逐级指路） |
| 3 | Cache-Control 是 HTTP/2.0 引入 | 是 HTTP/1.1 引入（RFC 2616），HTTP/2 沿用头部字段 |
| 4 | ETag 不支持是因为「老机器」 | 是服务器/中间件不一定实现（nginx 默认不生成）+ 生成哈希有开销 |
| 5 | 协商缓存不需要客户端配合 | 必须带 If-Modified-Since / If-None-Match 条件请求头 |
| 6 | 强缓存命中是 304 | 是 200 (from cache)；304 表示发过请求且协商命中 |
