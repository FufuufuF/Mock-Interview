> 方式：互动式教学（先讲后复述，含 QUIC 可靠传输细节追问）
> 大纲：`.agents/.session/network-review-outline.md` 第一章

---

## 一、一句话主线

**每一代 HTTP 都在解决上一代最痛的问题：**
- HTTP/1.0 痛点：一个请求一个 TCP 连接（握手 + 慢启动开销大）→ 1.1 用 Keep-Alive 复用连接
- HTTP/1.1 痛点：响应必须按请求顺序返回（队头阻塞）→ 2.0 用二进制分帧 + 多路复用
- HTTP/2 痛点：TCP 层队头阻塞 + 握手延迟 → 3.0 抛弃 TCP，基于 UDP 自建 QUIC

---

## 二、各版本演进对比

| 版本 | 核心变化 | 解决的问题 |
|------|----------|-----------|
| HTTP/0.9 | 只有 GET、只返回 HTML、无 header | 无（雏形） |
| HTTP/1.0 | header、状态码、POST/HEAD、多文件类型 | 表达能力不足 |
| HTTP/1.1 | Keep-Alive、Host 头、管线化、缓存控制 | 连接建立开销巨大 |
| HTTP/2 | 二进制分帧、多路复用、HPACK、Server Push | HTTP 层队头阻塞 |
| HTTP/3 | 基于 UDP 的 QUIC | TCP 层队头阻塞 + 握手延迟 |

## 三、HTTP/1.1 详解

### 3.1 改进点
1. **Keep-Alive（持久连接，默认开启）**：一个 TCP 连接串行处理多个请求
2. **Host 头**：一个 IP 上多个域名（虚拟主机），靠 Host 区分
3. **管线化（Pipelining）**：一次发多个请求，但**响应必须按请求顺序返回（FIFO）**

### 3.2 队头阻塞的双重来源
- **服务器端**：管线化要求响应按序返回——文本协议没有帧元数据，顺序是唯一的分流手段；前面请求慢（大文件），后面全部堵住
- **客户端**：实际管线化没普及（多数服务器/代理默认关闭），退化为「一个连接同时只能有一个请求在途」，发下一个请求必须等上一个响应

### 3.3 现实
浏览器靠**每个域名约 6 个并行 TCP 连接**弥补。6 个连接也是有限资源：连接总数上限（浏览器约 6~17 个），大量资源排队。

### 3.4 误区纠正
> ❌ 「HTTP/1.1 客户端可以直接一次性发起多个请求」
> ✅ 那是管线化特性，实际没普及；真实 HTTP/1.1 是一个连接上一个请求在途

## 四、HTTP/2 详解

### 4.1 三个核心机制

**① 二进制分帧层（Binary Framing Layer）**
- 文本协议 → 帧（Frame）为单位：HEADERS / DATA / RST_STREAM / SETTINGS / PING
- 每帧带 **Stream ID** 标识所属流
- 流（Stream）= 一个请求-响应交换；连接 = 一条 TCP 上跑多个流

**② 多路复用（Multiplexing）**
- 多个流交错传输、乱序到达，接收方按 Stream ID 重组
- 一个请求慢不阻塞其他请求
- **与 Keep-Alive 的本质区别**：Keep-Alive 是串行复用（同一时刻一个请求在途），多路复用是并行复用（帧级交错，多个请求同时在途）

**③ HPACK 头部压缩**
- 静态表：61 个高频字段预定义索引（`:method: GET` 只占 1 字节）
- 动态表：连接内首次出现的字段加入索引，后续用索引引用（header 高度重复）
- Huffman 编码压缩字段值

### 4.2 Server Push 与结局
- 服务器主动推送预测的资源 → 实际利用率低（客户端可能已缓存）
- **Chrome 106 已移除支持**，被 **103 Early Hints** 取代（提前返回预加载提示）
- 面试说法：「了解原理，但已被淘汰」= 加分项

### 4.3 残留问题：TCP 层队头阻塞
- HTTP/2 只解决**应用层**队头阻塞
- TCP 是字节流协议，**全局一个字节序列号**，必须按字节序交付给上层
- 丢一个包 → 重传期间接收缓冲区里**所有流**的数据都取不出来（哪怕别的流是完整的）
- 类比：一列火车各车厢独立了，但隧道一旦堵车整条隧道都堵

### 4.4 补充
- HTTP/2 规范不要求 TLS，但浏览器实现只支持 h2（HTTPS 上的 HTTP/2）→ **实践中必须配 HTTPS**
- 版本协商靠 TLS 握手 **ALPN** 扩展

## 五、HTTP/3 与 QUIC 详解

### 5.1 定位

```
传统（HTTP/2）:  HTTP/2 → TCP → IP       （TCP 在内核态，改不了）
HTTP/3:          HTTP/3 → QUIC → UDP → IP（QUIC 在用户态，随时改）
```

UDP 不保证到达/有序/防重复 → 可靠传输整套机制由 QUIC 在**用户态自己实现**（把 TCP 机制搬进应用层并改进）。

### 5.2 TCP 的四个「原罪」
1. **队头阻塞**：一个包丢失阻塞所有流
2. **握手延迟**：TCP 三次握手 1-RTT + TLS 1.3 握手 1-RTT，串行共 **2-RTT** 才能发第一个字节
3. **连接迁移困难**：四元组（源 IP、源端口、目的 IP、目的端口）标识连接，IP 变即断
4. **协议栈在内核**：改进依赖 OS 升级 + 中间设备（防火墙/NAT）配合，迭代极慢

### 5.3 QUIC 两层结构（关键模型）

```
┌─────────────────────────────────────────────┐
│  流层（逻辑层）:  Stream ID + Offset 拼接数据  │ ← 数据怎么拼回原样
├─────────────────────────────────────────────┤
│  包层（传输层）:  包号 + ACK 包号区间           │ ← 哪些包丢了要重传
└─────────────────────────────────────────────┘
```

**流层（拼数据）**
- 数据按 Stream 拆分，STREAM 帧带 `Stream ID + Offset + Length + Data`
- 接收方按 Offset 把块拼回完整字节流（每个流独立拼）
- 不负责重传决策

**包层（传数据）**
- 传输单位是**包（Packet）**，每包有**包号（Packet Number）**
- **一个包可装多个流的帧**（流 A 数据 + 流 B 数据 + ACK 帧打包发出）
- 接收方对「收到的包」发 ACK：`已确认包号 1~100，缺 57、89`
- 发送方对缺失包号重传，**重传用新包号**

### 5.4 与 TCP 可靠传输的关键区别

| | TCP | QUIC |
|--|-----|------|
| 确认单位 | 字节序号（ACK 号 = 期望的下一个字节） | 包号（范围列表，含缺口） |
| 重传是否复用序号 | 复用 → 重传歧义，RTT 测不准 | 用新包号 → RTT 精确 |
| 可靠性与数据组织 | 一体：一个全局字节流 | 分层：流层拼数据、包层管传输 |
| 丢包影响 | 全局阻塞（队头阻塞） | 只阻塞所在流 |
| 流量控制 | 连接级单一窗口 | 连接级 + 每流独立窗口 |
| 拥塞控制 | 内核固定实现 | 用户态可插拔（CUBIC/NewReno 默认） |

### 5.5 误区纠正（重点）
> ❌ 「每收到一个块就发 ACK，ACK 表示当前流中某个区间收到哪些块」
> ✅ ACK 是**连接级别**的，确认的是**包号区间**；流的字节偏移只用于重组数据。
> 流层发现数据拼不齐（Offset 空洞）→ 传输层知道对应包丢了 → 重传。
> 且 ACK 是**合并发送**的：每收 2 个 ack-eliciting 包或延迟最多 ~25ms 发一个 ACK 帧，避免 ACK 风暴。

### 5.6 其余三大特性

**① 内置 TLS 1.3（握手集成）**
- CRYPTO 帧承载 TLS 握手消息，所有数据包默认加密
- 首次连接 **1-RTT**，会话票据复用 **0-RTT**（客户端直接带请求数据出发）

**② Connection ID（连接迁移）**
- 连接由 Connection ID（客户端随机 64 位）识别，IP/端口只是「当前地址」
- Wi-Fi ↔ 4G 切换：带同一 Connection ID 从新地址继续发，连接不断、无需重握手

**③ 0-RTT 重放风险**
- early data（握手完成前发出的请求）可被截获重放，服务器无法区分新旧
- 只适用于**幂等请求**，或服务端防重放设计（时间戳窗口 + 一次性票据）

### 5.7 落地情况
- 浏览器全支持（UDP 443 + TLS 1.3 强制）；Cloudflare/Akamai 已大规模部署
- 坑：企业防火墙/老设备可能拦 UDP 443 → 降级链 `HTTP/3 → HTTP/2 → HTTP/1.1`
- 优势最明显：高丢包弱网、移动网络（连接迁移）、视频/实时通信

## 六、请求方法与状态码速查

### 方法
| 方法 | 语义 | 幂等 |
|------|------|------|
| GET | 取数据 | ✅ |
| POST | 提交 | ❌ |
| PUT | 整体替换 | ✅ |
| DELETE | 删除 | ✅ |
| PATCH | 部分修改 | ❌ |
| HEAD | 只要响应头 | ✅ |
| OPTIONS | 询问支持的方法（CORS 预检用） | ✅ |

### 状态码重点
- **301 vs 302 vs 307 vs 308**：301/302 在 POST 场景浏览器可能改写为 GET；307/308 保证方法不变。301/308 永久（浏览器缓存重定向），302/307 临时
- **304**：协商缓存命中
- **401 vs 403**：401 未认证，403 已认证无权限
- **429**：限流（LLM API 必见，配合 Retry-After 头）
- **502 vs 504**：502 网关收到上游无效响应；504 网关等上游超时

## 八、误区纠正记录

| # | 错误理解 | 正确模型 |
|---|---------|---------|
| 1 | HTTP/1.1 客户端可一次性发多个请求 | 那是管线化，实际没普及；真实是一个连接一个请求在途 |
| 2 | Keep-Alive 与多路复用类似 | 串行复用 vs 并行复用（帧级交错） |
| 3 | HTTP/2 解决了所有队头阻塞 | 只解决应用层；TCP 层（字节序交付）仍阻塞 |
| 4 | QUIC 的 ACK 确认「流中的字节块区间」 | ACK 是连接级包号区间；流内 Offset 只用于重组 |
| 5 | 每收一个块就回一个 ACK | ACK 合并发送（2 包或 ~25ms），单帧可确认多个包号区间 |
| 6 | 重传复用原序号 | QUIC 重传用新包号（RTT 精确），TCP 复用（重传歧义） |
| 7 | HTTP/3 = UDP 上的 HTTP/2 | HTTP/3 有自己的传输层协议 QUIC（可靠传输 + TLS 集成 + 连接迁移） |
