## 维度4：协程 → Generator → async/await

### 4.1 协程的概念

**协程（Coroutine）= 可暂停 + 可恢复的函数。**

类比：在书里夹一个书签，合上书去做别的事，回来后翻到书签继续读。

- 普通函数：调用后一路执行到 return，中间无法打断
- 协程函数：执行到某个点可以主动**让出（yield）**，之后可以从让出的位置**恢复（resume）**继续执行

关键特征：
1. 局部变量被保存（不会因为让出而丢失）
2. 执行位置被保存（恢复时从上次停下的地方继续）

---

### 4.2 底层实现原理

#### 编译器做了什么？

以 `yield` 为界，把一个协程函数拆成**状态机**：

```
原始代码：
function* gen() {
  const a = 1;
  const b = yield a;    // 切割点1
  const c = yield b+1;  // 切割点2
  return c;
}

编译器视角：拆成3个状态
state 0: const a = 1; return a; → 切到 state 1
state 1: const b = input; return b+1; → 切到 state 2
state 2: const c = input; return c; → done
```

#### 局部变量怎么保存？

**从栈提升到堆对象上。**

- 普通函数的局部变量在栈帧上，函数返回栈帧销毁，变量没了
- 协程函数的局部变量被提升到一个堆上的对象（Generator 对象），让出时栈帧可以释放，但变量还活着

---

### 4.3 Babel 转译层面（regenerator）

Babel 的 `regenerator` 把 Generator 转译成一个字面的 **switch 状态机**：

```javascript
// 转译后的伪代码
function gen() {
  var a, b, c;
  var _state = 0;
  
  return {
    next: function(input) {
      switch (_state) {
        case 0:
          a = 1;
          _state = 1;
          return { value: a, done: false };
        case 1:
          b = input;
          _state = 2;
          return { value: b + 1, done: false };
        case 2:
          c = input;
          return { value: c, done: true };
      }
    }
  };
}
```

**这不是杜撰的！** 真正去看 regenerator 的输出，就是这种 switch-case 结构。

---

### 4.4 V8 原生层面

V8 不需要做 switch 转译，它的实现更高效：

1. Generator 函数编译成字节码时，`yield` 位置会记录一个**字节码偏移量（bytecode offset）**
2. 让出时：保存当前偏移量 + 寄存器状态到 Generator 对象
3. 恢复时：直接跳回保存的偏移量位置继续执行

比 switch 状态机少了一层"翻译"，性能更好。

---

### 4.5 Stackless vs Stackful 协程

| 特性 | Stackless（JS/Python） | Stackful（Go goroutine） |
|------|----------------------|------------------------|
| yield 位置 | 只能在协程函数本体内 yield | 可以在调用栈任意深度 yield |
| 实现 | 状态机 / 保存偏移量 | 保存完整调用栈 |
| 内存开销 | 小（只保存本层变量） | 大（保存整个栈） |
| 灵活性 | 低（需要 yield 层层传播） | 高（深层函数可直接挂起） |
| 代表 | JS Generator、Python asyncio | Go goroutine、Lua coroutine |

JS 的 `await` 看起来可以"深层挂起"，其实是因为每个 async 函数都是独立的协程，层层 await 形成链式挂起。

### 4.6 Generator 语法

```javascript
function* myGen(x) {
  const y = yield x + 1;    // 向外输出 x+1，向内接收 next 传入的值
  const z = yield y * 2;    // 向外输出 y*2
  return z;
}

const g = myGen(5);
g.next();       // { value: 6, done: false }   — 执行到第一个yield，输出5+1
g.next(10);     // { value: 20, done: false }  — y=10，输出10*2
g.next(99);     // { value: 99, done: true }   — z=99，return
```

**yield 是双向通道：**
- 向外：`yield expression` 的 expression 值作为 `next()` 的返回
- 向内：下一次 `next(arg)` 的 arg 作为整个 yield 表达式的值

### 4.7 yield Promise + 自动执行器 = async/await

核心思路：如果 yield 出来的是 Promise，执行器等它完成再 `.next(result)` 喂回去。

```javascript
// 自动执行器（run 函数）
function run(generatorFn) {
  const gen = generatorFn();
  
  function step(value) {
    const result = gen.next(value);      // 唤醒协程，拿到 yield 的 Promise
    if (result.done) return result.value;
    
    // 等 Promise 完成 → 把结果喂回去 → 递归
    result.value.then(res => step(res));
  }
  
  step();  // 启动
}

// 使用
run(function* () {
  const data = yield fetch('/api');      // yield 一个 Promise
  const json = yield data.json();        // yield 又一个 Promise
  console.log(json);
});
```

**这就是 async/await 的全部本质！**

---

### 4.8 async/await = Generator + 引擎内置自动执行器

| 概念 | Generator 版 | async/await 版 |
|------|-------------|---------------|
| 声明 | `function*` | `async function` |
| 让出 | `yield promise` | `await promise` |
| 恢复 | 手动/执行器 `.next(value)` | 引擎自动恢复 |
| 执行器 | 手写 run 函数 | 引擎内置 |

#### await 一行到底发生了什么？

```javascript
async function foo() {
  const result = await somePromise;
  // ... 后续代码
}
```

精确步骤：
1. **让出**：协程执行到 await，暂停 foo 的执行，将控制权交还调用者
2. **注册回调**：引擎内置执行器对 somePromise 注册 `.then(唤醒函数)`
3. **继续事件循环**：此时 foo 已经让出，事件循环继续处理其他任务
4. **Promise 完成**：somePromise resolve 时，往微任务队列推入"唤醒 foo 协程"的任务
5. **微任务执行**：事件循环清空微任务时，执行唤醒 → foo 从 await 处恢复，result 拿到值

## 维度5：事件循环精确模型

### 5.1 破除误区

**错误理解**：宏任务 → 微任务 → 渲染，严格交替  
**正确理解**：不是严格交替！

---

### 5.2 精确模型

```
┌─────────────────────────────────────────┐
│            事件循环（一轮）               │
│                                         │
│  1. 从宏任务队列取出 1 个宏任务执行       │
│                                         │
│  2. 清空所有微任务                       │
│     （包括执行微任务过程中新产生的微任务）  │
│                                         │
│  3. 如果需要渲染（≈16.6ms 一次）：       │
│     a. 执行 requestAnimationFrame 回调   │
│     b. 渲染                             │
│                                         │
│  4. 回到步骤 1                           │
└─────────────────────────────────────────┘
```

**关键点**：
- 微任务是**清空式**的，不清完不会去取下一个宏任务
- 渲染不是每轮都有，浏览器按需决定（通常 60fps → 约 16.6ms 一次）
- 如果微任务无限产生新微任务 → 死循环，页面卡死

---

### 5.3 宏任务 vs 微任务分类表

| 宏任务（Macrotask） | 微任务（Microtask） |
|-------------------|-------------------|
| `setTimeout` / `setInterval` | `Promise.then/catch/finally` |
| 用户交互事件（click 等） | `queueMicrotask()` |
| `MessageChannel` | `MutationObserver` 回调 |
| I/O 完成回调 | `await` 后面的代码 |
| `<script>` 标签（第一个宏任务） | `process.nextTick`（Node） |
| `setImmediate`（Node） | |

---

### 5.4 第一个宏任务 = `<script>` 标签同步代码

浏览器加载页面时，`<script>` 标签里的同步代码就是第一个宏任务。执行完后立即清空微任务队列。

```javascript
// 这整段同步代码 = 第一个宏任务
console.log('D');                    // 同步
Promise.resolve().then(() => {
  console.log('B');                  // 微任务
});
setTimeout(() => {
  console.log('A');                  // 下一个宏任务
}, 0);
console.log('C');                    // 同步

// 输出顺序：D → C → B → A
// 第一个宏任务(同步)：D C
// 清空微任务：B
// 下一个宏任务：A
```

---

### 5.5 MutationObserver

- **作用**：监听 DOM 变化（属性、子节点、文本）
- **时机**：微任务！
- **为什么是微任务**：DOM 操作可能一帧内发生多次，用微任务可以在本轮"清空"时批量通知，避免多次同步回调

```javascript
const observer = new MutationObserver((mutations) => {
  console.log('DOM变了', mutations);  // 微任务时机执行
});
observer.observe(el, { childList: true });
```

---

### 5.6 requestAnimationFrame（RAF）

**RAF 既不是宏任务，也不是微任务**，它有自己的队列。

- 执行时机：在渲染前（步骤3a）
- 不是每轮事件循环都执行，只在浏览器决定渲染的那一轮执行
- 如果页面不可见，RAF 会暂停（省电）

---

### 5.7 优先级总结

```
同步代码 > 微任务 > requestAnimationFrame（如果本轮渲染）> 宏任务
```

验证代码：

```javascript
console.log('1-同步');

setTimeout(() => console.log('4-宏任务'), 0);

Promise.resolve().then(() => console.log('2-微任务'));

requestAnimationFrame(() => console.log('3-RAF'));

console.log('1-同步end');

// 确定输出：1-同步 → 1-同步end → 2-微任务
// RAF 和 宏任务的相对顺序：通常 RAF 先（在渲染帧内），但不绝对保证
```
